# Reusable package coordination — Athena project goal

Accepted goal, 2026-11-19. **Backlog, not an implemented universal package manager.** The shared design rule is [P8](PRODUCT-PILLARS.md#p8--modular-features-and-safe-independent-evolution); this document assigns Athena-specific coordination. Preserve existing implementations and private acceptance holds.

## Intent and ownership
Make compatible feature, game and ability packages discoverable, reusable, selectively installable and removable across participating repositories/apps. Users can choose only what they need while the rest of an app remains usable. Athena tracks authoritative package versions, consuming apps and compatibility evidence, and coordinates reviewed updates. It must not become a mandatory online dependency for local app startup or independently installed features.

## Existing source and limits
Reviewed [Feature Foundry README](https://github.com/Herbertofury/Feature-Foundry/blob/main/README.md): Living World studio modules include worlds/rooms, ecology, mascot, media, music and native persistence. These are reuse candidates, **not evidence of a hot-swappable cross-app package contract**. Athena's [preservation README](../feature-foundry/README.md) records preserved historical source and explicitly separates preservation from integration. Private native integration work does not establish public dynamic-package support. Keep original source, licenses, ownership and acceptance evidence intact; do not replace existing modules merely to introduce a framework.

## Implementation and acceptance backlog
- [ ] Inventory actual module boundaries and consumers before designing a minimal contract. Trial one genuinely reusable feature in two compatible hosts, not a large speculative framework.
- [ ] Define stable package identity, publisher/provenance, exact version/hash, contract/ABI/schema versions, OS/architecture/runtime requirements, host capabilities, required/optional dependencies, conflicts, permissions, license and data ownership. Unknown compatibility must not be represented as supported.
- [ ] Maintain installed and available versions separately; pin known-good versions, track consumers and show compatibility/update plans. Use event-driven bounded refresh and offline cached metadata with visible freshness, not constant polling.
- [ ] Support selective install/enable/disable/remove with an explicit dependency plan. Refuse removal of required dependencies or offer a clearly reviewed cascade; do not silently remove other features. Retain user data by default, with export/reinstall compatibility and separately authorized deletion.
- [ ] Stage and verify supported downloads, integrity and provenance before activation; avoid executing arbitrary untrusted packages. Least-privilege capabilities and appropriate process/runtime isolation must contain faults. Metadata and hashes alone do not prove safety.
- [ ] Specify prepare/start/quiesce/stop/dispose and state handoff. Cancel owned work and release listeners, timers, resources and handles before unloading. Admit live hot-drop only for explicitly supported contracts; otherwise require a safe restart, clearly stated before applying.
- [ ] Coordinate upgrades as staged transactions with compatibility checks, preserved prior artifacts/data and migration receipts. Test rollback, failure between stages, interrupted restart, disk-full and schema downgrade limits. Never promise rollback where migration is irreversible.
- [ ] Test host-alone operation, independent package operation where meaningful, missing optional components, dependency version mismatch, fault isolation, stale controls and install/update/remove/reinstall cycles. Run consumer contract and integration regressions, including preserved user settings/saves.
- [ ] Measure installed/download size, startup and interaction latency, frame time, memory and idle CPU/wakeups before/after; include disabled/uninstalled baselines. Pursue the owner's pure-benefit/no-tradeoff target: require no measurable regression against equivalent baseline workloads within documented measurement resolution, noise and coverage, including correctness and safe removal. If the gate fails, seek another solution or retain the current implementation. State unknowns rather than guaranteeing zero overhead on every workload.
- [ ] Record exact tested host/package/version combinations and shipped versus synthetic evidence. Do not mark compatibility, hot-unload or universal reuse complete from one fixture or metadata-only registry.

## Rust two-host proof: Cargo feature-unification acceptance
**Planned test, not an observed repository bug or an implemented/passing test.** Cargo features compose additively; disabling defaults on one dependency edge is not a global veto. A different dependency can enable them again. See the [Cargo Book: feature unification](https://doc.rust-lang.org/cargo/reference/features.html#feature-unification).

- [ ] Create a disposable two-host fixture around the chosen reusable Rust package: host A requests its minimal configuration with defaults disabled; host B exercises the explicitly enabled capability. Also test each host separately and any combined workspace/build selection actually intended for delivery.
- [ ] Add a deliberate transitive dependency path that re-enables the package's default or optional capability. Assert the resolved capability becomes enabled in that applicable build graph, then remove that enabling path and verify the intended minimal configuration. Do not assume separate binaries necessarily share one resolved feature set.
- [ ] For every configuration, capture `cargo tree -e features -i PACKAGE` (replace PACKAGE with the actual package/version specification), using the corresponding target, package selection and feature flags. Record toolchain, resolver, lockfile, manifests and exact commands. This explains feature activation; it is not binary-size, runtime or isolation proof.
- [ ] Build and test the actual minimal, explicit-enabled and transitively re-enabled configurations. Verify advertised capabilities and unchanged core behavior, then measure delivered artifact size, startup, memory and representative concurrent latency against equivalent baselines. Account for target-specific, build and dev dependency resolver behavior rather than assuming all invocations match.
- [ ] Keep compile-time omission separate from runtime disable/uninstall/hot-unload. Cargo flags select build contents; a UI toggle does not remove compiled code, and passing this fixture does not establish safe live package removal. Test runtime lifecycle, preserved data, dependency handling and recovery independently.
- [ ] Apply the no-measurable-regression gate before claiming a benefit. If transitive activation defeats the required minimal distribution, revise dependency boundaries/configuration and retest rather than advertising an absent feature or guaranteed size saving.

No installation, background watch, update dispatch, permission grant or runtime activation is created by this document.

## Owner directive: one shared capability source, continuous improvement

Athena is the canonical coordination and evidence hub for all owned repositories. Use the [shared capability routing index](../guidance/registry/shared-capabilities.json) as the entry point for overlapping implementations. It references the existing engineering research/source registers, adapter contracts, dated measurements and owning repositories; it does not replace or copy those catalogs. Individual projects retain their own product authority, runtime compatibility, data ownership, permissions, release cadence and independent portable operation.

### Consult, contribute, reuse

1. At the start of substantive work, inspect the existing project backlog and relevant Athena capability entry. Check current upstream research, existing internal implementations, active work and previous failures before creating another solution. Use stable capability IDs and exact version/commit references; do not infer absence from an incomplete search.
2. For a missing capability, add a small record to the existing index and assign a clear owning repository and scope when known. If an implementation already exists, evaluate reuse, wrap, port, compose or improve it before rebuilding. Compare actual source and equivalent complete workloads, not marketing or similar file names. Record candidates as unverified until measured; a research lead is not a recommended implementation.
3. Select the strongest verified compatible implementation per target/contract. Prefer one maintained source/library or adapter with versioned releases and host-specific bindings. Where sharing code is inappropriate, share contracts, fixtures, algorithms and evidence; preserve intentional variants with explicit compatibility reasons. Do not mandate a single implementation across incompatible languages, platforms, game versions, permissions or licenses.
4. Make improvements at the authoritative source when authorized, test them, and notify/review affected consumers through the shared record. Avoid copy-paste forks that silently drift. Pin the actual consumer version, contract, configuration and compatibility evidence; evaluate updates independently in each real host. Keep older verified consumers functioning until their new version is accepted. No forced fleet merges or online dependency at app startup.
5. Contribute reusable discoveries, benchmark receipts, bug reproductions, fixes, rejected alternatives and compatibility holds back to Athena during the same material checkpoint. Link original evidence and existing backlog items instead of copying them into multiple trackers. Record the next action and owner; do not mark unresolved work complete. Refresh stale observations when a capability is touched or before the next relevant release. The daily upstream discovery workflow is an input, not proof that all knowledge is fresh.
6. Before release, perform a bounded reuse/drift review for changed capabilities as part of the existing stack-freshness evidence: what is used, what stronger compatible implementation is available, what was adopted or repaired, and why any separate implementation or hold remains justified. No separate paperwork gate, universal rewrite or forced package extraction. The existing mandatory optimizer, fix-forward and opt-in security policies remain intact.

### Zero-loss evolution and organizational rules

- Keep a protected baseline for each project: accepted feature inventory, user-facing behavior, supported versions/platforms, data/schema, portability, performance, visual fidelity, native/runtime acceptance and last-good commit/artifact. Do not silently remove features, overwrite other agents' work, erase history, or trade completeness for apparent speed.
- Before consolidating duplicates, inventory both implementations and actual consumers. Identify unique features and preserve them in the new contract or host-specific adapter. Run side-by-side tests with identical workloads and validate at least two real compatible consumers before claiming cross-project reuse. Keep a staged rollback and preserve original source/history; delete/retire only with verified replacement and authorization.
- Make every reusable improvement a ratchet: pin evidence-backed winners, add regression fixtures for discovered defects, record failed approaches, and promote changes only after independent consumer verification. Use the existing repair-first modernization process before retaining an older eligible version.
- Keep a single source of truth for each capability and backlog item, stable links to local implementation evidence, explicit ownership and status, and a clear next action. A registry entry can be candidate, comparison-needed, canonical-policy-only or verified implementation; never turn source inspection into runtime proof. Avoid duplicate agents working the same scope: reconcile active work and branch/commit checkpoints before edits.
- Respect existing authorization, data and distribution boundaries. Preserve local portable storage and offline operation; Athena coordinates engineering, it is not a mandatory remote runtime for consumer apps.

The initial index is a partial source inventory, not a finished shared package manager. No internal implementation is declared superior before matched runtime evidence. The existing package coordination backlog above remains the implementation roadmap; extend it rather than creating another independent tracking system.

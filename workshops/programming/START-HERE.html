Give every value a meaning and a unit

Start a repair-quote calculator with explicit types, bounds and expected results.

You will learn to

  • Distinguish text, integer counts and display strings.
  • Keep amount arithmetic in explicit integer cents for the project.
  • Write a function contract before its implementation.

Learn

A useful program starts with a question precise enough to answer. Our fictional repair workshop needs a subtotal for supplied line items, not a payment system. Each line has a stock identifier, a quantity and a price in cents. Before writing code, decide the allowed input, the output and the behavior for invalid data. These choices form the program’s contract.

The text "3" and the integer 3 are different values. Repeating text and multiplying a quantity are different operations even when the same symbol appears. Conversion should happen at a defined boundary with validation, not everywhere a value is used. A display string such as "49.97" is for a reader; it is not the internal arithmetic representation in this project.

Use whole-number cents for the quote’s exact additions and multiplications. Two items at 1250 cents produce 2500 cents. This avoids binary floating-point approximation for this narrow arithmetic. Real currency systems also need currency identity, rounding rules, tax, discounts and other requirements. Integer cents is a project decision, not a claim that every financial domain has two decimal places.

State bounds deliberately. Quantity is an integer from 1 to 1000; unit_cents is an integer from 0 to 1000000. Zero-price items are valid, but zero quantity is not a line item under this contract. Python treats booleans as related to integers, so the validator requires an exact integer type rather than accepting true as one unit.

A contract also describes what does not change. validate_item returns a new flat dictionary and leaves the caller’s input untouched. Errors should be explicit rather than silently replacing invalid data with zero. The visible tests encode those decisions so that implementation and expectations can be discussed independently.

Open projects/repair_quotes/starter.py and implement one function at a time. The placeholders intentionally fail until you replace them. The reference file is available for comparison after you have tried the exercise. Do not copy a passing test result into your evidence as proof that you personally implemented the function; distinguish your work from running the supplied solution.

Worked example

For a line with sku=FILTER, quantity=2 and unit_cents=1250, the line subtotal is 2500 cents. format_cents(5) must produce "0.05", not "0.5". The validator rejects quantity=true even though a casual arithmetic expression might treat it as 1. These are explicit product choices tested at their boundaries. The program never charges anyone or contacts a merchant.

quantity = 2
unit_cents = 1250
line_cents = quantity * unit_cents
# line_cents is 2500; its unit is cents.
display = f"{line_cents // 100}.{line_cents % 100:02d}"
# display is "25.00", a presentation string.

Trace a loop before trusting its output

Build the subtotal by maintaining a simple invariant at every step.

You will learn to

  • Explain branch and loop behavior in a small trace.
  • Use a running-total invariant and a defined empty case.
  • Choose boundary tests that expose off-by-one and reset errors.

Learn

A program follows the control flow that its code expresses, not the intention in a comment. Conditions select a path; a loop repeats a body for a sequence of inputs. Indentation defines blocks in Python. When a result surprises you, trace the values before and after each relevant statement rather than changing several lines at once.

For the quote, initialize subtotal to zero before the loop. For each validated line, compute quantity times unit_cents and add that line amount once. A useful invariant is: after processing the first k lines, subtotal equals their sum. At the start k is zero and the empty sum is zero. After the last line, the invariant gives the desired total.

The location of an assignment matters. Resetting subtotal to zero inside the loop discards earlier work. Returning from inside the loop can stop after the first item. Including the last index twice can double-count. A three-line example often reveals these errors more clearly than a large file, because you can calculate each intermediate value by hand.

Define the empty case on purpose. Under this contract, an empty quote is valid and returns zero lines, zero units, zero subtotal and an empty grouping. That differs from an empty event summary’s mean, which is absent rather than zero. Similar-looking empty inputs can require different outputs because the questions differ.

Avoid modifying the sequence you are iterating over unless the behavior is deliberately designed. Here the input stays unchanged while separate accumulators build the answer. This makes the trace easier to explain and keeps a second caller from seeing unexpected edits. The next lessons extend the accumulators to grouped results.

The supplied trace_total example runs only fixed invented values and prints every step. Predict it before running. Seeing the expected final number once is useful, but the invariant explains why the algorithm should work for other allowed cases. Later tests exercise a bounded set of quantities and prices; they are evidence, not a proof over every possible program.

Worked example

The three fixture line amounts are 2500, 1497 and 1000 cents. The running totals are 2500, 3997 and 4997. If a loop resets the total on each iteration, the final value becomes 1000, a plausible-looking but wrong amount. The empty quote returns zero without entering the loop. Both the multi-line trace and empty case are required evidence.

subtotal = 0
for quantity, unit_cents in [(2, 1250), (3, 499), (1, 1000)]:
    line_cents = quantity * unit_cents
    subtotal += line_cents
# After each iteration: 2500, 3997, 4997.

Build small functions without hidden state

Separate calculation from I/O and avoid accidental mutation through aliases.

You will learn to

  • Give each function a focused input/output contract.
  • Distinguish returning a value from printing it.
  • Recognize aliasing and the limits of a shallow copy.

Learn

A function is a named operation with inputs and a result or effect. Small functions let you reason about one decision at a time. validate_item checks a row; quote_total calculates a summary; format_cents creates a display string. A command-line wrapper decides when to read a fixture and print JSON. Combining all those jobs in one loop makes failures harder to isolate.

Returning a value lets another function or test inspect and reuse it. Printing produces output for a user or another process. A calculator that only prints a number is harder to combine with grouping or formatting. Our project functions return ordinary data and do not read files, make requests or print; the wrapper owns those I/O choices.

Prefer explicit arguments over hidden global configuration for this exercise. A function whose result depends on a mutable global counter can change behavior across tests or repeated runs. A fresh accumulator inside each call prevents one summary from leaking into the next. Repeating the same pure calculation should produce an equal result without altering the supplied input.

Assignment can create another name for the same object. If alias = original, changing a mutable object through either name affects the shared object. A shallow copy creates a new outer container but can still share nested items. In the supplied example, copying a list of dictionaries does not automatically copy each dictionary.

Copy only what the contract requires. The quote and event rows contain flat primitive values, so building a fresh dictionary is sufficient for those rows. A future nested schema would need its own mutation policy. Deep copying everything is not a universal fix; it can duplicate data that should remain shared and add cost without clarifying ownership.

Modules help organize related functions. Importing a module should not unexpectedly run the CLI or overwrite a file. The provided scripts use an explicit main entry point. Their import paths are fixed to the bundled learner or reference module; this is a convenience for the exercise, not a sandbox for arbitrary untrusted code.

Worked example

original is a list containing {quantity:1}. alias refers to that same list. shallow = list(original) creates a different list, but shallow[0] and original[0] still refer to the same dictionary. Setting shallow[0][quantity] to 3 changes original too. A separate list made from new flat dictionaries keeps quantity=1 in this example. The aliasing demo reports all three relationships instead of claiming every copy is independent.

original = [{"quantity": 1}]
shallow = list(original)
separate = [dict(row) for row in original]
shallow[0]["quantity"] = 3
# original[0]["quantity"] is now 3.
# separate[0]["quantity"] is still 1.

Choose collections from identity and order

Group legitimate repeated items while rejecting conflicting event identities.

You will learn to

  • Use lists, dictionaries and sets for distinct purposes.
  • Distinguish repeated business lines from duplicate delivery.
  • Make output ordering and tie breaking explicit.

Learn

A list preserves a sequence of items. A dictionary maps a key to a value. A set records unique membership. Choose from the operation you need, not from which syntax looks shortest. The quote needs to preserve line count while grouping by stock identifier; the event summary needs to identify repeated delivery of the same event.

Repeated keys do not always mean duplicate data. Two FILTER lines can represent legitimate separate quantities, even at different prices in this project. Group them by adding quantity and line subtotal. Replacing one row with the last row would lose work. The output deliberately avoids inventing a single unit price for a group that may contain several prices.

Event identity has a different contract. An identical repeated event_id is one logical event delivered twice, so it should not inflate event metrics. The same ID with different normalized content is a conflict and causes rejection. Never apply one generic “remove duplicates” rule to every dataset without understanding what its keys mean.

Dictionaries make identity lookup direct and clear for these bounded inputs. This can avoid repeatedly scanning the already-seen list, although exact runtime depends on implementation and workload. The project has at most 200 event rows; clarity and correctness matter more than claiming a large performance improvement from a tiny fixture.

Deterministic output makes tests and diffs easier to interpret. Quote groups are sorted by SKU. Event groups are sorted by label using Python’s ordinary string ordering, not locale-specific human collation. Slowest events are sorted by descending duration, with event_id ascending as an explicit tie-breaker. Do not leave a tie to accidental input order.

Keep validation and aggregation connected. Before inserting an event into the ID map, validate its shape and values. A conflicting duplicate must not silently overwrite an earlier event. Both projects return newly constructed summaries and leave input lists and rows unchanged, so callers can compare before and after safely.

Worked example

The quote has FILTER twice: 2×1250 plus 1×1000 gives quantity 3 and subtotal 3500, not the last row’s 1000. The event fixture has five delivered rows but four distinct IDs. EVT-001 is repeated identically and counted once. EVT-001 and EVT-004 both take 100 ms, so EVT-001 precedes EVT-004 when the slowest list reaches that tie. A changed duration under EVT-001 is rejected as a conflict.

seen = {}
for event in validated_events:
    event_id = event["event_id"]
    if event_id in seen and seen[event_id] != event:
        raise ValueError("conflicting duplicate event_id")
    seen[event_id] = dict(event)
# Identical repeated IDs remain one logical event.

Reject bad input without hiding the reason

Separate syntax, schema and meaning, then make failure behavior testable.

You will learn to

  • Distinguish parsing from domain validation.
  • Reject ambiguous keys, malformed numbers and unsupported data.
  • Handle expected input errors without swallowing programming defects.

Learn

Parsing answers whether text follows a representation’s grammar. Validation asks whether the resulting values meet your program’s contract. Valid JSON can still contain the wrong root type, a negative quantity or an unknown field. CSV can have correct quoting but an invalid status. Keep these questions separate so an error points to the right layer.

Be explicit about acceptance rather than guessing what a user meant. Quote rows require exactly three keys; event rows require four. The JSON parser rejects duplicate keys, because silently taking one value can hide contradictory input. Both parsers have byte and row limits appropriate to these small exercises. These bounds are teaching controls, not a complete hostile-input defense.

CSV cells start as text. The event duration column accepts ASCII digit text in a bounded length, then converts it to an integer and checks the numeric range. It does not accept a sign, decimal point, spaces or a look-alike Unicode digit. These strict rules are stated in the project contract; other products may intentionally choose different input conventions.

Choose meaningful failure behavior. The quote rejects the entire invalid input rather than returning a partial subtotal that looks complete. The event summary rejects a conflicting ID rather than silently discarding one version. Error messages help locate the issue, but callers should not depend on every word of a message unless that wording is part of the public contract.

Use exception handling at a boundary where you can respond appropriately. The CLI reports expected validation failures and exits nonzero. It does not catch every exception and print a success-shaped empty report. During development, a traceback for an unexpected bug is useful evidence. Hiding it behind a generic “all fine” response makes debugging harder.

Do not evaluate data as program code. JSON and CSV parsing do not require eval, shell commands or importing a filename supplied by the data. The supplied runner chooses between fixed local starter/reference modules and fixed synthetic fixtures. Running your edited Python still uses your normal permissions; only run code you wrote or trust, because the exercise runner is not a security sandbox.

Worked example

The quote parser rejects an item that contains quantity twice, even if both values are integers. The event parser accepts a quoted label containing a comma because CSV quoting defines one field, but rejects duration="1.5" because this contract requires integer milliseconds. If row 3 is invalid, returning totals for rows 1 and 2 without an error would misrepresent the requested report. Tests therefore expect ValueError for the whole input.

if type(quantity) is not int or not 1 <= quantity <= 1000:
    raise ValueError("quantity must be an integer from 1 to 1000")
# Parse first, then validate the domain.
# Do not replace invalid quantities with zero.

Move structured data through a small command-line program

Use standard parsers, explicit encoding and a predictable output contract.

You will learn to

  • Read CSV quoting correctly and distinguish strings from parsed values.
  • Separate modules, the CLI wrapper and file I/O.
  • Verify a local JSON round-trip without overwriting user files.

Learn

Files carry bytes; a text encoding turns those bytes into characters. This workshop uses UTF-8 explicitly. Structured formats add another layer: CSV describes rows and quoting, while JSON describes values and containers. Neither format should be interpreted by ad hoc string operations when a supported parser can express the rules.

Splitting a CSV line on every comma is not a CSV parser. A quoted label such as "repair, detail" is one field. The event project uses the standard CSV reader and requires an exact header and column count. It then converts only the duration field under its explicit lexical rules. Header-only input is a valid empty dataset here; a blank data row is not.

Keep the command-line wrapper small. It chooses a fixed project and implementation, reads one bounded bundled fixture, calls pure functions and writes one JSON result to standard output. Expected input problems go to standard error with a nonzero exit status. This makes the result easier for a person or another program to distinguish from an error.

The wrapper defaults to your starter, so an unfinished implementation reports that it is unfinished. Selecting reference is an explicit way to see the supplied solution’s behavior, not a claim that your starter passed. Importing a reference module does not run the CLI or create a file because execution is guarded by its entry point.

The JSON round-trip example writes one invented report to a new temporary directory, reads it back and compares the logical result. It exercises actual local I/O while protecting existing files. It removes only that created directory on normal completion. This does not test atomic replacement, power-loss durability, permissions or an independent backup.

A report should state units and scope. The event mean is a floating-point millisecond value for the supplied distinct events, not an SLO or production latency guarantee. An empty dataset has mean=None because no observations exist. Serializing that value to JSON gives null. Zero milliseconds would falsely suggest an observed average of zero.

Worked example

The fixture’s quoted repair, detail label remains one field, so the parser produces five rows. After identity deduplication there are four events, total duration 800 ms and mean 200.0 ms. The quote CLI prints subtotal_cents=4997 and display_subtotal="49.97". The JSON example separately verifies a temporary file round-trip. None of these commands reads a personal file or contacts a service.

import csv
import io
rows = list(csv.reader(io.StringIO('label,duration_ms\n"repair, detail",200\n'), strict=True))
# rows[1] is ["repair, detail", "200"].
# The duration is still text until deliberately converted.

Make a test distinguish a real mistake

Use boundaries, regressions and invariants instead of collecting green badges.

You will learn to

  • Read a failing assertion and form a small debugging hypothesis.
  • Write a regression that fails on a known defect.
  • Use deterministic property checks without claiming exhaustive proof.

Learn

A test compares observed behavior with an expectation. A passing test is useful only if the expectation matches the intended contract and the test actually reaches the relevant behavior. “The program ran” is weaker than checking the exact subtotal, output shape, duplicate policy and input preservation.

Start with one small failing case. Read the assertion, input and traceback; reproduce it; state a hypothesis; change one relevant cause; then rerun the focused test and the full project suite. Do not rewrite the expected value merely because the implementation produced something different. If the contract is wrong, revise it deliberately and explain the consequences.

The bug-hunt example uses floor division for a mean. For durations 1 and 2, that returns 1 instead of the required 1.5. A fixture whose mean is already an integer would miss the defect. The supplied regression explicitly distinguishes the buggy and corrected functions. This is a concrete reason to choose cases that exercise a difference.

Boundary tests explore the edges of allowed input: zero-price, minimum/maximum quantity, just-outside bounds, empty data, duplicate IDs, malformed CSV and a conflicting late row. A negative test should verify the intended failure, not accept any unrelated crash as success. Here public validation failures are ValueError; unfinished starters raise NotImplementedError and therefore do not accidentally satisfy those tests.

Useful properties complement exact examples. Reversing valid quote rows should preserve the summary. Adding an identical event delivery should increase duplicate_rows without changing unique metrics. A bounded grid of quantities and prices checks the multiplication rule across more than one example. Such loops cover the chosen finite cases, not all inputs or all future changes.

Repair Quotes contract

This is a fictional subtotal calculator. There is no seller, charge, tax, discount, currency conversion or payment integration. Names and prices are synthetic. All four functions return data, do not print, do not read files and do not mutate their inputs. Invalid input raises ValueError (including its subclasses); exact error wording is not part of the contract.

validate_item(item)

Input is a dictionary with exactly sku, quantity, unit_cents. No extra or missing keys are accepted.

  • sku: string of 1–20 ASCII uppercase letters A–Z, digits 0–9 or hyphens. No trimming or case conversion is performed.
  • quantity: exact Python int, from 1 through 1000 inclusive. Booleans, floats and numeric strings are rejected.
  • unit_cents: exact int, from 0 through 1,000,000 inclusive. Zero is allowed. Booleans are rejected.

Return a new flat dictionary with those three validated values. It must compare equal to valid input but must not be the same dictionary object.

quote_total(items)

Input is a list of at most 100 validated-or-unvalidated item dictionaries; validate every row. Empty input is valid. Return a new dictionary with exactly these fields:

  • line_count: number of input rows, integer.
  • unit_count: sum of quantities, integer.
  • subtotal_cents: sum of quantity × unit_cents across all rows, integer.
  • by_sku: list sorted by SKU in ordinary Python string order. Each member has sku, aggregate quantity and aggregate subtotal_cents.

Repeated SKUs are legitimate lines, including lines with different unit prices. Add their quantities and individual line subtotals. Do not deduplicate them or invent a single group price. An empty list produces 0, 0, 0 and []. The maximum allowed subtotal is 100,000,000,000 cents. Reversing input order preserves the full summary. No partly computed answer is returned if a late row is invalid.

format_cents(cents)

Input is an exact int from 0 through 100,000,000,000 inclusive. Return a decimal display string with exactly two fractional digits and no currency symbol or grouping commas. Examples: 0 → "0.00"; 5 → "0.05"; 4997 → "49.97". Keep integer arithmetic; avoid converting through a binary float.

parse_quote_json(text)

Input is a Python string whose UTF-8 encoding is at most 8192 bytes, inclusive. Decode JSON, require a list of at most 100 rows and validate every item using the contract above. Return a new list of fresh validated dictionaries.

Reject duplicate JSON object member names at any level, even if values match. Reject the nonstandard NaN, Infinity and -Infinity forms accepted by some decoder defaults. Reject malformed JSON, invalid row shape/types/bounds and a non-list root. JSON numbers such as 1.0 do not become integer quantities merely because their value is whole. Empty JSON list [] is valid. Byte length, not character count, is the limit.

A bounded parser is not a universal hostile-input defense. This teaching program only consumes the bundled synthetic fixture through its wrapper. It is not an upload endpoint or a financial system.

Fixture and checkpoints

fixtures/quote.json contains FILTER 2 × 1250, BRUSH 3 × 499, FILTER 1 × 1000. Line amounts are 2500, 1497 and 1000; total is 4997 cents. FILTER aggregates to quantity 3/subtotal 3500; BRUSH to quantity 3/subtotal 1497. Group order is BRUSH, FILTER.

Event Summary contract

Summarize a bounded synthetic event dataset. This is not telemetry collection, production monitoring, a log-upload service or a distributed delivery guarantee. All three functions return data, do not print or read files and leave caller-owned inputs unchanged. Invalid input raises ValueError (including subclasses); exact wording is not required.

validate_event(event)

Input is a dictionary with exactly event_id, label, duration_ms, status.

  • event_id: string matching EVT- followed by 3–6 ASCII digits. No case conversion or trimming.
  • label: Python string with 1–40 characters, no leading/trailing whitespace and no characters U+0000 through U+001F. This is a deliberately narrow character policy, not a general Unicode sanitization rule. Internal ordinary spaces and commas are allowed. Length counts Python string characters, not encoded bytes or displayed glyphs.
  • duration_ms: exact Python int from 0 through 600000 inclusive. Booleans, floats and numeric strings are rejected by this function.
  • status: exactly the string ok or failed.

Return a new flat dictionary containing the four normalized fields. No data transformation beyond the separately specified CSV duration conversion is performed.

parse_events_csv(text)

Input is a string of at most 16384 UTF-8 bytes, inclusive. Use the standard CSV reader with strict parsing enabled and newline-preserving text input. The first record must be exactly these columns in this order:

event_id,label,duration_ms,status

At most 200 data records are allowed. Each has exactly four fields. Duration text must be 1–6 ASCII digits, then convert to integer and validate the row. Leading zeros are allowed; signs, surrounding spaces, decimals, exponent notation and non-ASCII digits are not. The numeric upper bound remains 600000. A correctly quoted comma is part of the label, not a fifth field. CSV syntax failures reported by the strict reader are rejected. This does not claim to implement every possible external CSV dialect or RFC rule.

Header-only input is valid and returns []. Empty input, wrong header order, extra or missing columns and blank data records are rejected. A normal final line terminator is not an extra blank record. A byte order mark is not silently removed from the exact header. Do not replace parsing with split(',').

summarize_events(events, slowest_limit=3)

Input is a list of at most 200 events, each validated. slowest_limit is an exact integer from 0 through 10 inclusive. Default is 3; booleans are rejected.

An identical normalized event with the same ID is repeated delivery of one logical event. Count it only once in all event metrics. The same ID with any different normalized field is a conflict and raises ValueError. Do not silently overwrite conflicting content. Duplicate counting applies only to event IDs in this project, not quote SKUs.

Return a dictionary with:

  • input_rows: count of supplied rows.
  • unique_events: count of distinct valid event IDs.
  • duplicate_rows: input_rows minus unique_events.
  • successes and failures: counts across unique events.
  • total_duration_ms: sum across unique events.
  • mean_duration_ms: total divided by unique count using ordinary Python division, or None for no events. The float is an approximate summary, not an exact currency amount.
  • by_label: list of dictionaries with label, events, failures, duration_ms, computed from unique events, sorted by ordinary Python string order of label, not locale collation.
  • slowest: up to slowest_limit dictionaries with event_id, duration_ms. Sort descending by duration, then ascending by event ID. A limit of 0 returns an empty list.

Empty input has zero counts and total, None mean and empty group/slowest lists. Reversing input preserves the full result. Each call creates fresh accumulators; inputs and earlier results remain unchanged.

Types and arithmetic

Quantity and unit price are exact integers; their units are units and cents per unit. The product is cents. Display text is a string and does not replace the numeric amount. True is related to integers in Python, but this contract rejects it with an exact type check. 1.0 and "1" have different types. Boundary decisions come from the stated contract, not accidental coercion.

The three line subtotals are 2500, 1497, 1000. Running totals are 2500, 3997, 4997. The empty list has all zero counts and an empty grouping. Resetting inside the loop loses prior amounts; returning inside it can ignore later lines. At each iteration, subtotal equals the sum of all rows processed so far.

Integer cents avoids floating approximation for this exact sum/product, but this pack has no currencies, rounding policies, tax, exchange rates or payment behavior. The event mean is a different question and can be fractional.

Aliasing and state

An alias names the same list. A shallow list copy has a new outer list but still shares inner dictionaries. Changing its first dictionary also changes the original. A list of new flat dictionaries does not share those dictionaries, so its quantity remains 1 while the original becomes 3. This is only sufficient because nested mutable values are absent. Per-call accumulators and fresh result dictionaries prevent later calls from changing earlier results under this schema.

Identity

BRUSH totals 3 units/1497 cents; FILTER totals 3 units/3500 cents. A repeated stock item is not automatically a duplicate mistake. The two FILTER prices differ, so the grouped result reports totals and no invented unit price.

Five event deliveries represent four unique IDs. EVT-001 repeats identically. Unique durations sum to 800 ms, average 200.0; there are 3 successes and 1 failure. Groups sort as inspection, repair, repair, detail. The last item is one label containing a comma. Slowest order is EVT-002, EVT-003, EVT-001, EVT-004; default output takes the first three. Reversing input does not change this. A changed duration for EVT-001 conflicts with its identity and raises ValueError.

Validation

Missing/extra JSON fields, duplicate member names, NaN and float quantities are rejected. Syntax success alone is not semantic validation. Quoted CSV commas are valid inside a field. Empty CSV is rejected; header-only CSV gives no events. A blank data record is invalid. +5 and 5.0 fail the duration text rule; 005 becomes 5; 600001 parses as integer but fails the numeric bound. The file byte limits and row limits are separate checks.

NotImplementedError means a starter placeholder still needs implementation. It is not a corrupt fixture. Targeted input errors should not hide unrelated defects. The wrapper reports anticipated invalid input or unfinished work, but lets unexpected exceptions remain visible for debugging.

Define the question and the row grain

Turn an ambiguous service-desk question into a metric contract before querying.

You will learn to

  • State what one row represents in each table.
  • Specify a metric population, numerator, denominator and snapshot.
  • Separate a cohort status measure from events occurring during a period.

Learn

An analysis begins with a decision and a question, not a chart type. “How are tickets doing?” is too vague to test. Ask which tickets, which period, which status definition, which unit and which audience. A query can run successfully while answering the wrong question, so write the intended interpretation before trusting a result.

The grain is what one row represents. In this pack, tickets has one current-state row per ticket identifier; touches has one interaction row per interaction identifier; queues has one descriptive row per queue. Multiple touches can belong to one ticket. Those grains are different even when two tables share a ticket_id column.

Our main population is tickets opened from November 1, 2026 at 00:00 UTC up to, but not including, November 3 at 00:00 UTC. Status and work values come from an invented frozen snapshot labelled November 5. The question is the share of that opening cohort whose snapshot status is closed. It is not the number closed during those two days.

The CSV has no resolution timestamp, historical status changes or service-level target. Therefore it cannot establish when closure happened, how long resolution took or whether an SLA was met. Do not fill those gaps with assumptions because a dashboard would look more complete. A useful limitation explains exactly which missing field or definition prevents the stronger conclusion.

Microsoft’s star-schema guidance distinguishes descriptive dimensions from observations or events and emphasizes consistent granularity. The small queue table plays a descriptive role here. This is an introductory relationship design, not a complete Power BI semantic model or a warehouse with historical dimension management. Keep the business meaning ahead of any tool-specific labels.

Run the profile command to verify nine tickets, nine touches and four queues. Equal row counts do not mean one-to-one relationships: their keys and relationships determine that. Record the source as synthetic fixtures, not real company records. Your final handoff should make the population, grain, time basis and missing evidence easy for someone else to repeat and challenge.

Worked example

Seven tickets belong to the main opening cohort, and five have closed snapshot status: 5/7, about 71.4%. That does not mean five were resolved inside the reporting window. There are nine total tickets and nine total touch rows, but some tickets have several touches and others none. Matching table counts do not establish matching row identities.

SELECT COUNT(*) AS all_ticket_rows FROM tickets;
-- The reporting cohort adds an explicit opened_at interval.
-- Status describes the frozen synthetic snapshot, not a closure event time.

Load CSV with explicit types and missing-value rules

Validate bounded text before inserting it into an in-memory database.

You will learn to

  • Treat CSV fields as text until explicitly converted.
  • Distinguish missing work minutes from recorded zero.
  • Explain what parser checks and database constraints each enforce.

Learn

CSV is a transport format, not a schema. A field that looks numeric still arrives as text under the normal CSV reader. Quoting can place a comma inside a single field, so splitting each line on commas would break the summary “Screen, hinge.” Use a CSV parser and verify the exact header and number of columns before interpreting values.

The ticket contract maps an empty work_minutes field to Python None and then SQL NULL. A field containing 0 becomes the integer zero. Empty does not mean no work occurred; it means the value is missing in this dataset. The literal text NULL is rejected rather than quietly treated as missing. These are explicit ingestion choices, not universal CSV rules.

The loader accepts only bounded fixtures, exact headers, unique primary identifiers, fixed-width valid UTC timestamps, allowed status values and minute values from zero through 1440. It rejects an invalid row instead of silently dropping it. A discarded row would change counts and rates, so any future quarantine policy would need a visible rejection report and reconciliation.

Database constraints add another line of checking. STRICT tables enforce SQLite’s stricter storage types; primary keys, foreign keys and CHECK constraints express additional rules. STRICT does not mean every input string is rejected: SQLite can perform permitted lossless conversions. The Python parser separately enforces the text grammar and validates actual calendar dates.

Keep data values separate from SQL syntax by using bound parameters for inserts and filters. A quote in a label should remain data, not change a statement. Parameter binding does not validate business meaning or safely choose arbitrary table names; it addresses how values enter a statement. The pack uses fixed table and query names, with no external database target.

Every run builds a new in-memory SQLite database from the synthetic CSV files. It does not open an existing database or user spreadsheet. Work in a private pack copy when experimenting, preserve the original fixture and record any changed assumptions. A successful import demonstrates these local contracts only, not a general-purpose pipeline for unknown files or confidential records.

Worked example

T-003 has recorded work_minutes=0; T-002 and T-005 are open with missing work values; T-009 is closed with missing work. Closing a ticket does not make its missing measurement zero. The quoted comma stays inside T-001’s summary. The loader’s accepted rows and the database’s keys must agree before aggregation begins.

INSERT INTO tickets
  (ticket_id, queue_id, opened_at, status, work_minutes, summary)
VALUES (?, ?, ?, ?, ?, ?);
-- Python supplies a separate tuple; None becomes SQL NULL.

Filter a population and order it deliberately

Use explicit UTC boundaries and stable ordering to make a cohort reproducible.

You will learn to

  • Express a half-open interval with bound values.
  • Predict included boundary rows and excluded neighbors.
  • Distinguish filtering from display ordering and row limiting.

Learn

Filtering chooses which records belong in the analysis. The main query uses opened_at greater than or equal to the start and less than the end. This half-open interval includes the first instant and excludes the next period’s first instant, so adjacent periods can meet without counting their shared boundary twice.

The fixture deliberately tests both edges. T-001 opens exactly at November 1 midnight and is included. T-008 opens one second earlier and is excluded. T-007 opens exactly at November 3 midnight and is excluded from the main interval. Predicting these three rows is a small but powerful check of the intended population.

All stored timestamps are validated fixed-width UTC strings ending in Z. Under that narrow representation, lexical order matches chronological order. Do not extend that conclusion to mixed formats, offsets, unpadded dates or locale-dependent text. The parser rejects those forms; a real source would need a documented normalization and timezone policy.

ORDER BY controls how the selected rows are presented, not which rows satisfy the filter. The query orders by opened_at and ticket_id, making ties deterministic. Without an explicit order, do not build a report on whichever row order SQLite happens to return. LIMIT can restrict output, but it is not a random sample or a substitute for a population definition.

Read the statement in terms of the question: identify the table, select the opening interval, project the needed columns and order the result. The engine may execute it differently internally; the conceptual explanation is not a promise about a query plan. This exercise has tiny data and makes no performance benchmark claim.

Compare the seven selected identifiers with a hand-built list before calculating a rate. If counts disagree, investigate the boundary or source rule instead of adjusting the expected answer to match. A clear cohort extract is useful evidence for later aggregates and joins, because it lets another reader inspect exactly which tickets contributed.

Worked example

The main ordered cohort is T-001, T-002, T-003, T-004, T-005, T-009, T-006. T-009 is before T-006 because its opening time is 11:00 versus 20:00 on November 2. The interval includes November 1 midnight and excludes November 3 midnight. Adjacent intervals therefore do not both include T-007.

SELECT ticket_id, opened_at, status, work_minutes
FROM tickets
WHERE opened_at >= :start AND opened_at < :end
ORDER BY opened_at, ticket_id;

Calculate counts and averages without erasing missingness

Use denominator-aware SQL to distinguish rows, observations and absence.

You will learn to

  • Explain COUNT(*), COUNT(column), SUM and AVG on this dataset.
  • Show why NULL and zero produce different evidence.
  • Use a safe denominator and label a cohort rate accurately.

Learn

An aggregate compresses records, so its definition must preserve what matters. COUNT(*) counts rows. COUNT(work_minutes) counts non-NULL measurements. Those answers differ in this cohort: seven tickets but only four observed work values. Reporting the average without its observation count would hide a major limitation of the data.

The observed values are 30, 0, 45 and 30 minutes. Their sum is 105 and their average is 26.25. The zero participates because it is a recorded value; the three NULLs do not. Replacing each NULL with zero would change the question and produce 15 minutes per ticket across all seven, an assumption the source does not justify.

Conditional aggregation counts records matching a definition. The query counts five closed snapshot statuses and divides by seven cohort tickets. Multiplying by 1.0 ensures a real-valued ratio rather than an unintended integer-style result. NULLIF protects an empty denominator; an undefined rate should remain absent rather than be presented as a meaningful zero.

The empty case is part of the contract. With no matching tickets, row and category counts are zero, while the work sum, observed mean and closed share remain NULL. A group with tickets but no observed work is also different from a group with a recorded total of zero. Keep those distinctions visible in a report or exported data dictionary.

An average alone does not describe a distribution, explain causation or measure resolution time. This dataset records a snapshot work measure, not a full time history. Differences between queues could reflect missing data, case mix or reporting practice. The tiny fictional sample cannot establish that one real team performs better than another.

Run the metrics command and reconcile each value to the four observed measurements and seven ticket rows. Then run the groups command to see Repair, Access, Setup and the empty Training queue. Compare each group’s ticket count, observed-value count and missingness before forming a conclusion. Evidence quality belongs beside the metric, not in a footnote that changes its meaning.

Worked example

Main result: 7 tickets, 5 closed, 4 observed work values, 3 missing, 1 recorded zero, total observed work 105 and mean 26.25. Closed share is 5/7. Access has three tickets but only one observed work value, zero; Training has no cohort tickets and an undefined mean/rate. Those are not equivalent situations.

SELECT COUNT(*) AS tickets, COUNT(work_minutes) AS observed,
       SUM(work_minutes) AS observed_total, AVG(work_minutes) AS observed_mean
FROM tickets
WHERE opened_at >= :start AND opened_at < :end;

Prevent join fan-out from changing the metric

Expose a wrong total, reject a tempting DISTINCT patch and fix the grain.

You will learn to

  • Predict one-to-many row multiplication.
  • Explain why distinct numeric values are not distinct business records.
  • Preaggregate detail rows before joining to a ticket-grain measure.

Learn

A join combines matching records. When a ticket has several touches, joining its row to each touch repeats its ticket-level fields. This can be useful for an interaction-level question, but summing a repeated ticket measure answers a different question. Before joining, state the expected relationship and the grain of the resulting rows.

The naive left join expands seven cohort tickets to ten joined rows. T-001 appears twice and T-004 appears three times because of their interactions. Summing ticket work_minutes across those rows produces 225, not the correct 105. The SQL is valid; the metric is wrong because the grain changed.

COUNT(DISTINCT ticket_id) can recover the number of distinct tickets for that specific count, but it does not repair every repeated measure. SUM(DISTINCT work_minutes) is an especially tempting mistake. T-001 and T-006 legitimately both have 30 minutes. Distinct values collapses them into one 30, producing 75 and undercounting real observations.

The corrected query first groups touches to one row per ticket, with a touch count and touch-minute sum. Joining that result to tickets preserves the ticket grain. The report then has seven ticket rows, 105 observed ticket work minutes, seven touch rows and 55 touch minutes for the cohort. These are separate measures, not two totals that are required to equal each other.

Left joins preserve unmatched left records, but later filters can undo that intention. In the queue summary, the date condition is inside the join’s ON clause so Training remains present with zero matched tickets. COUNT(t.ticket_id) counts matches; COUNT(*) would count the placeholder row and misleadingly report one for an empty queue.

Treat cardinality as something to test, not a relationship icon to trust. Compare before/after row counts, distinct identifiers and known measure totals. Include repeated equal numeric values in a test so a DISTINCT shortcut cannot appear correct by accident. If a new source changes the relationship, revisit the metric definition before shipping a familiar-looking chart.

Worked example

Naive: 10 rows and repeated work total 225. SUM(DISTINCT work_minutes): 75. Correct preaggregation: 7 ticket rows and 105 work minutes. Touches separately total 7 rows and 55 minutes. The fixture deliberately contains two real 30-minute ticket measurements, which exposes the incorrect distinct-value repair.

WITH per_ticket AS (
  SELECT ticket_id, COUNT(*) AS touches, SUM(minutes) AS touch_minutes
  FROM touches GROUP BY ticket_id
)
SELECT COUNT(*) AS ticket_rows, SUM(t.work_minutes) AS work_minutes
FROM tickets AS t LEFT JOIN per_ticket AS p ON p.ticket_id = t.ticket_id
WHERE t.opened_at >= :start AND t.opened_at < :end;

Build a complete time series with an explicit window

Use a calendar to preserve zero-event days and a window function for a running total.

You will learn to

  • Distinguish an absent date from a verified zero count.
  • Keep daily and main-cohort windows clearly labelled.
  • Use a deterministic cumulative window over grouped daily data.

Learn

A time series can hide days with no records. Grouping only ticket rows produces dates that exist in the data; it does not prove anything about dates that are absent. A calendar provides the expected reporting dates. A left join can then preserve each date and count its matching tickets, including zero when the source coverage is known.

The dates exercise intentionally uses a wider interval than the main metrics: November 1 through November 4 UTC, ending exclusively at November 5 midnight. Its calendar contains exactly those four days. The main cohort still ends at November 3 midnight. A total can differ legitimately when the population changes, so print the interval beside the output.

Daily opening counts are 3, 4, 1 and 0. The November 3 ticket is included in this wider series but excluded from the main cohort. November 4 remains present because it is in the calendar even though no ticket opens that day. In real data, a zero is credible only if ingestion coverage is known; an outage in collection is not automatically zero activity.

The query first produces one row per day, then applies a running SUM ordered by day with an explicit ROWS frame from the beginning through the current row. The cumulative counts are 3, 7, 8 and 8. The window calculation retains daily rows, unlike a final aggregate that would collapse the entire series to one total.

This pack uses validated UTC timestamps and UTC-midnight boundaries. It does not convert a local business day, handle daylight-saving changes or align regional calendars. Those are requirements to define before analyzing a real organization’s daily activity. The fixed calendar rejects intervals outside its coverage rather than quietly returning an incomplete series.

Check the first day, final exclusive boundary, zero day and final cumulative total. Compare the series total with a direct count using the same wider interval, not with the narrower seven-ticket metric. A correct reconciliation uses the same population and unit on both sides. Labeling those choices makes a small chart or table easier to interpret without inventing a trend from four synthetic days.

Worked example

The wider dates output has November 1: 3, November 2: 4, November 3: 1, November 4: 0; running totals 3, 7, 8, 8. The eight-ticket series is consistent with the seven-ticket main cohort because T-007 is added by the wider window. Neither output is a real demand forecast.

SELECT day, opened_tickets,
       SUM(opened_tickets) OVER (
         ORDER BY day ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
       ) AS running_opened_tickets
FROM daily
ORDER BY day;
-- daily is the calendar-based common table expression in dates.sql.

Use constraints and rollback to protect the dataset

Reject a broken relationship and verify that a partial import does not remain.

You will learn to

  • Verify foreign-key enforcement on the actual connection.
  • Observe a real in-memory transaction rollback.
  • Separate structural consistency from truth and business validity.

Learn

Data quality has several layers. A unique identifier can prevent duplicate keys; a foreign key can require a referenced queue to exist; a CHECK constraint can reject an invalid status or minute range. These are useful structural rules, but they do not prove that a report describes reality or that its measurement definition is appropriate.

SQLite foreign-key enforcement must be enabled and checked for the connection rather than assumed from a schema declaration. The lab sets PRAGMA foreign_keys=ON before loading and verifies the returned setting. It also uses STRICT tables, while the parser handles the tighter source-text rules. Each layer has an explicit purpose and an observable test.

The quality exercise starts a transaction and inserts a valid synthetic ticket T-900. It then attempts T-901 referencing nonexistent queue Q-Z. That foreign-key failure is expected. The handler explicitly rolls back the transaction, removing the earlier valid insert as well. The database returns to nine tickets, and T-900 is absent.

A failed statement and a rolled-back batch are not automatically the same event. Error handling must decide and verify the intended transaction outcome. The pack uses explicit BEGIN, COMMIT and ROLLBACK on its owned in-memory database so the boundary is visible. Do not infer behavior for another driver mode or database engine without checking its documentation.

The command also checks for foreign-key violations and runs an integrity check. An empty violation list and an “ok” result are useful local evidence, not proof of complete business quality. A plausible but wrongly recorded work value can satisfy every schema constraint. Missingness, coverage, reconciliation and stakeholder definitions still need review.

All mutations occur in a fresh private in-memory database created for this run. No existing database or external service is opened. The exercise is deliberately safe for practicing failure and recovery, but it is not a crash-durability or concurrent-writer test. Preserve the expected failure in your evidence rather than hiding it to make every step look successful.

Data dictionary and contracts

Provenance and time basis

All data is synthetic. The invented snapshot label is 2026-11-05T00:00:00Z. Main cohort: opened_at ≥ 2026-11-01T00:00:00Z and < 2026-11-03T00:00:00Z. The daily exercise alone ends at 2026-11-05T00:00:00Z. Status and cumulative work describe the snapshot, not events that necessarily occurred inside the opening interval. No resolution timestamp, SLA target or status history is available.

Tables and grain

  • queues: one descriptive row per queue_id. queue_id matches Q- followed by one uppercase ASCII letter; queue_name is unique, nonempty descriptive text.
  • tickets: one current-state row per ticket_id, matching T- plus three ASCII digits. queue_id must refer to queues. opened_at is a valid fixed-width UTC timestamp YYYY-MM-DDTHH:MM:SSZ. status is open or closed. work_minutes is a nullable integer from 0 through 1440. summary is nonempty text. Work is a recorded ticket-level measure, not resolution duration.
  • touches: one interaction per touch_id, matching X- plus three ASCII digits. ticket_id refers to tickets. minutes is a non-null integer from 0 through 1440. These interaction minutes are separate measurements, not required to equal ticket work.
  • calendar: one row for each UTC date November 1–4, 2026. This is a finite fixture, not a global date dimension.

Queues and tickets have a one-to-many relationship. Tickets and touches also have one-to-many potential. Some queues have no cohort tickets; some tickets have no touches. Every identifier must be unique within its own table, but identical numeric measurements across different tickets are legitimate.

CSV ingestion

parse_csv(kind, text) supports only queues, tickets and touches, with exact headers and column order shown in the fixtures. Input is a string of at most 32768 UTF-8 bytes and at most 1000 data rows. The CSV reader uses strict mode and newline-preserving input. Malformed CSV reported by that reader, extra/missing columns and duplicate primary identifiers are rejected with ValueError. A normal final newline is not an empty extra record; an actual blank data record is invalid. Header-only input is permitted.

Fields begin as text. Minutes must be 1–4 ASCII digits and convert to an integer in 0–1440. Signs, spaces, decimals, non-ASCII digits and literal NULL are rejected. Only ticket work_minutes may be empty, mapping to None/SQL NULL. Zero remains zero. Labels are 1–100 trimmed characters with no U+0000–U+001F controls; quoted internal commas are valid. Timestamps must have valid calendar dates and exact UTC Z format; mixed offsets or fractional seconds are not accepted.

The parser validates one file’s shape and values. Cross-file foreign-key relationships are checked by SQLite during loading. It does not silently discard or impute rows. These are teaching-schema rules, not a universal CSV convention or a public upload security boundary.

SQLite construction and lifetime

Requires SQLite 3.37+ for STRICT tables. connect() creates only :memory:, enables/verifies foreign keys and loads the bundled schema. load_database() parses the fixed fixtures and loads them in one explicit transaction. A failure rolls the load back and closes the connection. Every CLI command uses a fresh database and closes it in a finally block. No existing database is opened.

STRICT tables still allow applicable lossless type conversions; they do not replace source-text validation. The schema checks primary/foreign keys, allowed status and minute bounds. Calendar validation is performed by the Python parser, not a comprehensive SQL date constraint.

Queries and parameters

query(conn, name, window) accepts only filters, metrics, groups, joins_naive, joins_correct or dates. Query files are fixed, trusted source capped at 8192 bytes. Window contains exactly start and end, both valid canonical UTC timestamps with start < end. Values are bound separately; they are not concatenated into SQL.

The dates query additionally requires midnight boundaries and an interval contained in November 1 through November 5 exclusively. It uses the four-row calendar. Other queries can evaluate any valid interval against the fixed dataset. Output is a list of dictionaries. Filters have explicit opened_at/ticket_id order; groups sort by queue_name/queue_id; dates sort by day.

The templates are trusted teaching code, not a sandbox for arbitrary SQL. Do not add ATTACH, external connections, extension loading or user-file operations. The CLI accepts no arbitrary SQL or file path.

Metrics and missingness

COUNT(*) counts selected ticket rows; COUNT(work_minutes) counts observed non-NULL measurements, including zero. Work sum/mean use observed values only. Empty population counts are zero; work sum, mean and closed_share are NULL. closed_share uses closed snapshot statuses divided by cohort tickets, with an undefined result for zero denominator. It is not an in-period closure flow, SLA percentage or resolution-time measure.

The groups query preserves all queues with a LEFT JOIN and date conditions in ON. Training’s zero matched tickets do not make its absent work sum/mean/rate zero. The naive join is intentionally wrong for summing ticket-level work. The corrected join preaggregates touches to one row per ticket.

Quality and export exercises

quality_demo makes and explicitly rolls back an invalid two-row batch inside the owned in-memory database. The first valid insert must not remain. It verifies foreign-key enforcement, unchanged row count, no relationship violations and structural integrity. It does not prove business truth, crash safety or concurrent-writer behavior.

export_demo runs the queue query and uses a standard CSV writer inside a new owned temporary directory. It rereads the output as text, verifies each field against the documented string conversion, and cleans up the directory. None becomes an empty field; numeric values become text. This is a verified practice export, not a persistent output report or unknown-spreadsheet sanitizer.

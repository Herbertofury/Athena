Describe the service before choosing the cloud

Separate cloud characteristics, service models and deployment models using one fictional workload.

You will learn to

  • Explain the five NIST characteristics in ordinary language.
  • Distinguish service model from deployment model.
  • Write a workload contract before naming a vendor product.

Learn

Cloud is an operating model, not a synonym for any remote computer. NIST describes five essential characteristics: self-service provisioning, broad network access, pooled resources, rapid elasticity and measured use. A hosted server that needs a support ticket for every capacity change may still be useful, but a label alone does not show which cloud characteristics it provides.

Service models describe what the consumer receives and controls. IaaS provides infrastructure on which the consumer manages operating systems and applications. PaaS offers a managed application platform. SaaS supplies an application the consumer uses. Real solutions combine models, and the boundary depends on the specific service. A convenient service name is not a complete responsibility agreement.

Deployment models answer a different question. NIST distinguishes private, community, public and hybrid clouds by use and composition. Private does not simply mean physically in your office. Public does not mean your data should be publicly readable. Hybrid is a composition with integration between distinct cloud infrastructures; two unrelated vendor accounts do not by themselves explain an architecture.

Our fictional workload is a workshop report service. Staff submit small reports; a dashboard reads them; a background job prepares summaries. Start with who uses it, which data is retained, normal and peak demand, downtime tolerance, data-loss tolerance and the team’s operating skills. These requirements help compare options before an attractive product name biases the decision.

Write a service contract in plain language: what must work, who maintains each part, what can fail, what evidence would demonstrate success and what is out of scope. A managed database may reduce one maintenance burden while adding service limits or recovery choices you still need to understand. Fewer servers to administer does not mean no operational decisions remain.

This workshop does not open an account or deploy the fictional service. You will classify a workload, calculate bounded scenarios, inspect a local change report and perform one actual temporary-file restore. Those activities build reasoning habits. They do not demonstrate provider-console fluency, real network behavior, service quotas or a successful cloud deployment.

Worked example

The team could run its own application on virtual machines, deploy it to a managed runtime or buy a suitable hosted reporting application. The choice changes control and work, not the underlying need to manage users and data. Record two requirements that favor each option, then one uncertainty to check in current service documentation. Do not infer that the cheapest-looking compute rate answers the entire decision.

Practice safely

  1. Write a five-line description of the fictional report service and its users.
  2. Explain each NIST characteristic with your own example and counterexample.
  3. Classify three candidate approaches as IaaS, PaaS or SaaS, noting mixed components.
  4. State a deployment model separately from the service model.
  5. List five questions that must be answered before a real deployment.
  6. Mark the entire cloud deployment as unexecuted in your evidence worksheet.

Assign responsibility and limit the scope

Identify retained duties and compare a narrow resource scope with a broad one.

You will learn to

  • Name customer duties that do not disappear in a managed service.
  • Explain hierarchy and inherited scope without treating vendors as identical.
  • Detect a misleading string-prefix scope match in a local model.

Learn

Shared responsibility is a division of work, not an escape from accountability. AWS describes responsibility for underlying infrastructure separately from customer-controlled components. Microsoft’s matrix likewise keeps data, identities and configuration decisions with the customer while management of operating systems and other layers changes by service model. Read the specific service boundary rather than memorizing one diagram as universal law.

For our report service, someone must decide who can read reports, remove departing staff, review configuration and verify recovery. A provider can operate a physical host without knowing whether a particular colleague should see a particular report. Make an owner-and-evidence list: task, accountable owner, how completion is checked and when that check happens.

Resource hierarchies help organize ownership and policy. Google Cloud uses organizations, optional folders and projects; Azure documents management-group, subscription, resource-group and resource scopes. Inherited scope can make a single assignment affect many descendants. These are examples, not interchangeable identifier formats or proof that all policy evaluation rules are the same.

The offline scope exercise uses invented paths such as academy/dev/reports. It compares whole path segments. A scope of academy/dev includes that report resource but not academy/dev-tools/reports. A careless text-prefix test would confuse those siblings. This is a small programming model of containment, not an IAM simulator that determines effective cloud permissions.

Scope is only one part of authorization. A real decision also depends on the principal, operation, role or policy, conditions and provider-specific interactions. The exercise creates no role assignment and holds no identity credential. Broadening academy/dev to academy merely shows which invented resources fall under a larger boundary; it does not grant anyone access.

Least privilege needs a concrete task. If a study role only needs development reports, explain why production reports are outside the task rather than selecting a broad role for convenience. Also plan how legitimate access is reviewed and removed. A narrow diagram with no lifecycle owner is incomplete, while a broad inherited assignment can make a small mistake affect more resources.

Worked example

The narrow scope academy/dev matches one fixture resource. The broad scope academy matches all three: development reports, production reports and development-tool reports. The similar-looking dev-tools segment is not a child of dev. The result reveals containment only. It does not establish actual read permission, evaluate deny policies or authenticate any user.

Practice safely

  1. Assign owners for data access, guest-OS patches in IaaS, service configuration and restore verification.
  2. Read one provider’s current responsibility guidance and note where the boundary depends on service choice.
  3. Predict the narrow and broad scope results.
  4. Run python3 labs/cloud-workshop/run_lab.py scope.
  5. Explain why dev-tools is not inside dev in the invented model.
  6. Record what a real authorization test would still need, without creating credentials or grants.

Trace access and choose a data interface

Keep routing, network rules, service behavior, identity and storage semantics distinct.

You will learn to

  • Separate assumed network reachability from authorized application access.
  • Compare object, file and block interfaces by workload need.
  • Explain why storage durability is not the same as a recoverable backup.

Learn

A request can fail at several layers. A route may be absent, a network rule may exclude traffic, a service may not be listening or the application may reject an identity. Treat these as different hypotheses. Opening a wider network range does not fix a stopped process or missing application permission, and it can create unnecessary exposure.

AWS security groups are one provider example of controls on associated resources’ traffic. Their rules and stateful behavior are specific to that service. Our exercise does not implement them. It simply receives four explicit boolean assumptions and reports whether all are true. No packet is sent, no firewall is changed and no actual identity is tested.

Data interfaces also differ. Object storage addresses objects through a service interface, file storage provides shared-file semantics and block storage supplies disk-like blocks for a host or other consumer. Azure documents examples of each; S3 is an object-storage example. Choosing among them starts with how the application reads and writes, not with a generic request for more storage.

The fictional report documents fit an object-oriented access pattern, while an application that requires a shared filesystem may need a different interface. That is a starting hypothesis, not a universal recommendation. Check update patterns, consistency behavior, metadata, maximum sizes, access controls and integration requirements for the exact service before committing to a design.

Separate durability, availability and recoverability. Data can remain intact while a service is temporarily unavailable. A highly durable copy can faithfully preserve an accidental overwrite or an unwanted change. Recovery planning therefore needs a usable earlier point, retention decisions and a tested way to restore, not merely confidence that a storage service rarely loses bits.

In the fixture, the route and network assumptions pass but the service-listening assumption fails. A second case passes those three but fails the identity assumption. Neither result diagnoses a live system. Write what evidence you would collect next, such as authorized service-health observations or an intended user’s access result, without scanning a target or broadening permissions.

Worked example

The network command returns service_listening as the failed baseline assumption and identity_allows for the second case. It does not claim an actual connection was blocked. For storage, write why a report object and a virtual-machine disk have different access patterns. Later, the restore exercise will prove only that a local synthetic earlier copy can be recovered into a new file.

  2. Predict both fixed network-model results.
  3. Run python3 labs/cloud-workshop/run_lab.py network.
  4. Choose an object, file or block interface for three invented needs and explain each choice.
  5. Give an example of durable data that still needs recovery from an earlier point.
  6. List which network and storage behaviors remain untested in a real cloud.

Calculate capacity without inventing elasticity

Use an explicit target and maximum to understand what scaling can and cannot solve.

You will learn to

  • Calculate replicas from demand and per-instance capacity with units.
  • Distinguish a utilization target from a physical ceiling.
  • Identify omitted startup, quota and dependency constraints.

Learn

Elasticity is the ability to adjust resources as demand changes; it is not unlimited instant capacity. A scaling design needs a signal, a target, minimum and maximum capacity, and assumptions about how additional instances help. A service can add workers while its database, lock or external dependency remains the bottleneck.

AWS Auto Scaling offers target-tracking and other dynamic policies with service-specific behavior and bounds. We use an original, much simpler arithmetic model: identical replicas appear immediately, distribute work evenly and each have a fixed request-per-minute capacity. The model has no actual utilization metric, warm-up time, queue or cloud quota.

Write the units before the calculation. At 400 requests per minute per replica and a 50 percent target, the planning allowance is 200 requests per minute per replica. For demand 850, divide by 200 and round upward: five replicas are needed at the target. Rounding down would knowingly omit capacity from the planning calculation.

The configured maximum is four, so the local plan returns four and marks the target unmet. Their modeled physical capacity is 1600 requests per minute, but the 50 percent planning allowance is only 800. Both statements can be true: the physical ceiling is not exceeded while the desired headroom is missing. Do not label every target miss an observed outage.

A minimum can preserve baseline capacity during quiet periods; a maximum can limit expansion. Neither is a substitute for understanding cost, startup delay or graceful overload behavior. An apparently generous maximum can still be unreachable if quotas, placement constraints or a downstream service limit intervene. Those real constraints are not represented by the local integer calculation.

Predict changes before editing a study copy of the fixture. What happens at demand zero, exactly 800, just above 800 or far above physical capacity? Keep the original distribution tests unchanged so your modified scenario is not confused with a broken pack. Record your assumptions and explain why a load test against an authorized deployed service would be a separate, unexecuted activity.

Worked example

The fixed command needs five replicas but plans four. It reports target capacity 800 rpm and physical capacity 1600 rpm for demand 850. target_met is false, physical_capacity_met is true, and capped_by_maximum is true. These are arithmetic outcomes, not provider telemetry or an actual autoscaling event.

  5. In a private fixture copy, compare demand 0, 800, 801 and 1700, recording each prediction.
  6. Name four real scaling constraints the model omits.

Check the capacity that survives a failure

Place replicas across invented zones and calculate whether the remaining capacity is useful.

You will learn to

  • Explain a failure domain without assuming complete independence.
  • Calculate surviving capacity rather than counting zones alone.
  • Separate a capacity check from an availability or SLA claim.

Learn

A failure domain is a boundary within which one event can affect several components. Two processes on one host share a host failure. Several hosts in one location can share a power or network dependency. Separating replicas can reduce some shared risks, but the meaningful boundary depends on the system and the failure being considered.

AWS describes Availability Zones as isolated infrastructure groupings within a Region. Its guidance makes continued operation conditional on correct application architecture. A multi-zone label is therefore not a guarantee that your workload survives a zone loss. Application placement, dependencies, remaining capacity and recovery behavior still matter.

Our baseline has four identical replicas: two in invented zone-a and two in zone-b. Losing zone-a leaves two replicas. Each supports 400 rpm physically, but at the 50 percent target the survivors offer only 400 rpm of planning allowance. The workload demand is 500 rpm, so it had enough target capacity before the failure but not afterward.

An alternative places three replicas in each zone. Losing one zone leaves three and 600 rpm of target capacity, enough for the same assumed demand. The comparison demonstrates headroom arithmetic, not that buying two replicas is always the right solution. Other architectures might reduce demand, improve per-instance capacity or accept a different service objective.

Do not multiply imagined availability percentages and present the result as a measured guarantee. Dependencies can be correlated: a shared database, configuration rollout, identity service or client route can affect replicas in several zones. The local model removes only the named zone’s replicas and assumes all other components work. It has no measured failure rates or durations.

State the failure scenario precisely and ask what still needs testing. A zone-loss capacity calculation does not validate traffic redirection, health checks, data consistency, session handling or recovery from a regional event. Those require separately authorized real-environment exercises and explicit success criteria. In this pack every such cloud exercise remains unexecuted.

Worked example

Baseline: four replicas supply 800 rpm at the target; after losing zone-a, two supply 400, below demand 500. Alternative: six supply 1200; after the same loss, three supply 600 and meet the modeled target. Neither case measures user-visible availability or proves that failover would happen.

  3. Run python3 labs/cloud-workshop/run_lab.py failure.

  5. Write one additional failure scenario that the model cannot answer.
  6. Label actual failover, consistency and recovery testing unexecuted.

Measure the recovery gap and verify a local restore

Distinguish recovery-time and recovery-point targets, then recover invented data safely.

You will learn to

  • Compute downtime and the age of the recoverable data point.
  • Compare those observations with separate RTO and RPO targets.
  • Verify a real local copy/restore without claiming cloud disaster recovery.

Learn

Recovery objectives translate workload impact into testable targets. RTO concerns the acceptable time from service interruption to restoration. RPO concerns the acceptable gap between the recoverable data point and the incident. They answer different questions: how long service can be unavailable and how much recent work could be missing, expressed here in minutes.

A target is not a result. Define it with the people affected by downtime and data loss, then test a recovery method against it. An objective written in a diagram does not cause a backup to finish, an operator to be available or an application to restart. Dependencies and restore verification belong in the plan, not as afterthoughts.

Our invented timeline uses minutes from a fixed origin. The last recoverable point is minute 580, the incident is at 600 and service is restored at 650. The recoverable-data gap is 20 minutes and downtime is 50 minutes. Against RPO 15 and RTO 60, the scenario misses RPO while meeting RTO. Fast enough recovery can still restore data that is too old.

A backup schedule alone does not prove the most recent point is usable. A job can fail, a copy can be incomplete, an access dependency can be missing or an application can reject restored data. Verify recovery content and application behavior in an appropriate test. The strength of the evidence depends on what was actually restored and checked.

The separate restore command performs a real but tiny local exercise. It creates an owned temporary directory, writes invented report bytes, copies an earlier version, changes the source and restores the earlier copy into a new file. SHA-256 comparisons verify that the restored bytes match the earlier version, while the current source differs. It then cleans up only its own temporary directory.

This byte-for-byte local check does not establish cloud storage durability, encrypted-backup key access, database consistency, regional recovery or the fictional timeline’s measured duration. Do not time the tiny file operation and call it the service’s RTO. Keep two evidence labels: a synthetic recovery timeline and an actual local file-restore check. Real-cloud recovery remains unexecuted.

Worked example

The recovery command reports a 20-minute data gap and 50-minute downtime: rpo_met=false, rto_met=true. The restore command independently reports that backup and restored content match the original, current source differs, and the temporary directory was removed. No user file is replaced, no account is contacted and no disaster is caused.

  4. Run python3 labs/cloud-workshop/run_lab.py restore and inspect all verification flags.
  5. List three application-level recovery checks that byte equality does not cover.
  6. Record the timeline as modeled, the file restore as local execution and cloud DR as unexecuted.

Forecast usage and keep budget alerts in perspective

Calculate an explicit fictional bill and compare always-on with scheduled compute.

You will learn to

  • Multiply compatible usage and rate units.
  • Keep continuing storage and transfer costs visible.
  • Explain why a budget notification is not an instant spending cap.

Learn

A cloud estimate is a model of usage and rates, not merely a virtual-machine price. Record the period, compute hours, retained storage, requests or transfers that matter, and the services you left out. A small rate multiplied by an unexpected duration or number of resources can dominate the result. Units make those assumptions inspectable.

This exercise deliberately uses fictional credits, not currency or any provider’s prices. Three replicas run for 720 hours at five credits per replica-hour: compute costs 10800 credits. Storage contributes 100 GiB-months times two credits, or 200. Transfer contributes 50 GiB times three credits, or 150. The total is 11150 credits against a 10000-credit planning budget.

The alternative runs those replicas for 160 hours while leaving the same storage and transfer assumptions. Compute becomes 2400 credits and the total becomes 2750. This is not a promise that stopping a real instance eliminates every charge. Attached storage, retained data, networking components or commitments may continue to matter, depending on the exact service and terms.

A useful estimate shows what changes and what does not. In our comparison only compute hours change. Calling the scheduled plan cheaper is justified within those assumptions; calling it suitable for a round-the-clock service is not. Service availability requirements and operational startup behavior must be considered before changing any real schedule.

AWS Budgets documents delayed cost information and notifications. A notification threshold therefore must not be treated as a guaranteed instant hard cap. Provider budget actions have their own scope and behavior. This pack neither configures a budget nor stops resources. It simply compares an arithmetic result with a fictional threshold.

For an eventual authorized cloud lab, establish the account owner, allowed services, total spending limit, cleanup checklist and a method to verify remaining resources and charges. Current prices and free-offer terms would need fresh checking at that time. No free tier is assumed here. All exercises are local and create no billable cloud resources; the estimate itself is not a financial commitment.

Worked example

Always-on totals 11150 fictional credits and exceeds the 10000 threshold by 1150. Scheduled totals 2750 and is 7250 below it. Storage and transfer remain 350 in both. The 720-hour period is a stated 30-day assumption, not every calendar month. No value in this exercise is an AWS, Azure or Google Cloud quote.

  2. Calculate the three cost components and total for both schedules.

  5. List missing real-estimate items such as request charges, taxes, support or commitments.
  6. Write a future lab budget/cleanup checklist while marking account and billing work unexecuted.

Three original checks

Review a change before calling it a deployment

Compare desired state, identify risky changes and deliver an honest evidence packet.

You will learn to

  • Distinguish a local desired-state comparison from an executed change.
  • Flag removals, replacements and increased exposure for review.
  • Combine coverage, assumptions and unexecuted cloud work in a handoff.

Learn

Infrastructure as code describes infrastructure in reviewable form, but a file is not the running environment. Desired configuration, observed state and the actions a tool proposes can differ. A disciplined workflow separates preparing a change, reviewing its consequences, authorizing execution and verifying the result. Each stage needs its own evidence.

CloudFormation change sets are one provider example of previewing proposed effects before execution. The documentation also warns that a preview does not guarantee a successful update. Our local exercise is simpler: it compares two invented JSON inventories. It never calls CloudFormation, Terraform, another provider API or an apply operation.

The invented resource schema has id, kind, size and public fields. New IDs are additions; missing IDs are removals. A changed kind is modeled as replacement; other changed fields are modifications. These rules belong only to the teaching schema. A real provider may replace a resource for entirely different property changes, so this report cannot predict its behavior.

The fixture removes reports storage, adds queue compute and changes web size while making it public. The report highlights possible data/service loss from removal and increased exposure from the public change. It does not decide those changes are authorized or safe. A valid syntax check cannot supply missing business intent, data-retention requirements or an approved audience.

Build an evidence packet for the fictional service: workload contract, responsibility owners, scope comparison, network assumptions, scaling and failure calculations, recovery timeline, actual local restore and cost estimate. For each item state whether it is a prediction, local execution or unexecuted cloud work. An impressive number of green tests cannot turn a simulation into a deployed system.

Before any real lab, define an authorized isolated environment, bounded spending, data classification, rollback or recovery method, verification criteria and cleanup. Do not run an apply, grant access or create resources as an extension of this pack. The module ends with a reviewable plan and local evidence, leaving real provisioning, IAM, networking, failover and billing verification explicitly unexecuted.

Worked example

The change report is ordered by resource ID: add queue, remove reports, modify web fields public and size. It carries applied=false and warnings for reports removal and web exposure. Comparing an inventory to itself produces no changes. A reviewed plan is useful preparation, but it is not an executed deployment, a permission grant or a guarantee that a future provider operation succeeds.

Local lab guide

Boundaries first

Use a private study copy and synthetic data only. The Python code uses the standard library and no provider SDK. There are no accounts, credentials, network requests, purchases, resource changes, permission grants or live failovers. No cloud CLI or container runtime is required.

The eight fixed commands print JSON. Each output explicitly says real_cloud_executed: false. Seven are arithmetic or comparison models. The restore command creates one owned temporary directory, writes and copies invented report bytes, restores into a new file, and cleans up its own directory. It never reads or replaces a personal file. It does not test cloud durability or a real application’s recovery.

Python executes with your normal account permissions, not in a sandbox. Read the supplied code, edit only your study copy and do not paste untrusted code. No administrator permission is needed. No command accepts an arbitrary file path, URL or cloud target. A reference link is for reading, not an instruction to sign up or deploy.

Suggested rhythm

Predict the output, run the fixed command, explain any difference and record the limits. Use the worksheet and consult the answer key afterward. The full model contracts define bounds and assumptions. Expect roughly six hours of study plus additional reflection and variation work.

All commands below run from the extracted pack directory. If your platform uses python or py -3, substitute its Python 3 launcher. Only Python 3.12.14/Linux was executed here. Paper alternatives are valid study activities, but not execution evidence.

Model contracts

The functions in lab.py are original teaching models. They do not reproduce vendor APIs. They return new results, leave supplied inputs unchanged and raise ValueError for input outside their stated bounds. Exact error wording is not part of the contract. All numeric input described as integer requires an exact Python int, excluding booleans.

Scope

scope_contains(scope, resource) accepts two invented paths of 1–200 characters, with 1–8 slash-separated segments. A segment starts with a lowercase ASCII letter followed by at most 31 lowercase letters, digits or hyphens. Empty, dot, leading/trailing-slash and uppercase segments are invalid. Containment requires the complete scope segment sequence to be the resource’s initial sequence. Equality counts as containment. It is not string-prefix matching or effective authorization.

Connection gates

connection_checks(route_present, network_allows, service_listening, identity_allows) accepts exact booleans. It returns the assumptions, all_assumed_gates_pass and the failed assumption names in that parameter order. It does not check reality, send traffic or infer an order of diagnosis from timing.

Replica planning

replica_plan(demand_rpm, capacity_rpm, target_percent, minimum, maximum) accepts demand 0–1,000,000 rpm; capacity 1–1,000,000 rpm per replica; target 1–100 percent; minimum and maximum 0–1000 replicas with minimum ≤ maximum.

Needed-at-target is the ceiling of demand × 100 / (capacity × target_percent). Planned replicas clamp that count to the minimum and maximum. The return includes needed/planned counts, target capacity, physical capacity, whether each meets demand and whether the maximum capped the needed count. Comparisons use integer cross-multiplication; displayed target capacity can be a float. A zero-demand/zero-replica plan meets both arithmetic capacity checks. No warm-up, queue, dependency, instance weights, quota, availability or performance prediction is included.

Failure scenario

failure_report(placements, failed_zones, demand_rpm, capacity_rpm, target_percent) accepts 1–1000 placement strings matching zone-a through zone-z. Each list entry is one replica. Failed zones must be a list of zones present in placements; repeated failure names have the same effect as one occurrence. Demand, capacity and target have the replica-planning bounds. Remove all replicas in failed zones, then compute before/after target capacity and remaining physical capacity checks. The return includes sorted unique represented/failed zone lists. No probabilities, SLA, failover or correlated dependencies are modeled.

Recovery timeline

recovery_report(last_recoverable_minute, incident_minute, restored_minute, rpo_target_minutes, rto_target_minutes) accepts integers 0–1,000,000 with recovery point ≤ incident ≤ restoration. Data gap = incident minus recoverable point. Downtime = restoration minus incident. Meeting an objective includes equality. It reports each interval, target and comparison. The inputs are synthetic timestamps relative to one fixed origin, not date parsing or measurement of cloud events.

Cost arithmetic

cost_estimate(...) accepts eight integer values 0–1,000,000: replicas, hours, compute_credits_per_replica_hour, storage_gib_months, storage_credits_per_gib_month, egress_gib, egress_credits_per_gib, budget_credits. The three components are replicas × hours × compute rate, storage usage × storage rate and egress usage × egress rate. Total is their exact integer sum. within_budget includes equality; difference_from_budget is total minus budget, so negative means below budget. Rates are fictional credits, not currency. Storage usage is an already aggregated GiB-month quantity, not inferred from compute runtime. No taxes, tiered rates, requests, discounts, commitments or provider billing behavior are modeled.

Inventory change report

plan_changes(before, after) accepts lists of at most 100 resources. Each resource has exactly id, kind, size, public. ID is a lowercase-letter-led identifier of at most 32 ASCII lowercase letters, digits or hyphens; duplicates within either list are invalid. Kind is compute or storage; size is integer 1–1000; public is exact boolean. Size is an abstract schema quantity, not a portable cloud SKU.

IDs sort lexically. Missing old ID means add; missing new ID means remove. For retained IDs, changed fields sort lexically. Kind changes are modeled as replace; otherwise changes mean modify. Unchanged entries produce no change. All removals receive a risk note; replacements receive a risk note; new public resources or false-to-true public changes receive exposure notes. Risk notes are prompts, not an exhaustive risk assessment. Result always has applied: false; there is no apply function.

Actual local restore

restore_roundtrip() has no inputs. It creates an owned temporary directory, writes fixed synthetic report bytes, makes an earlier copy, changes the source and writes the copy to a separate restore file. SHA-256 checks the backup/restored bytes against the original digest. It reports those checks, current-source difference, byte counts and cleanup after the context closes. It does not return a reusable path, inspect user files or simulate cloud storage semantics.

Fixed wrapper

run_lab.py accepts only scope, network, scaling, failure, recovery, cost, changes or restore. The fixture file path is fixed; reads are capped at 32768 bytes. The restore command needs no fixture. No arbitrary path, URL, credential or provider is accepted. JSON stdout identifies local model versus actual local file exercise and always marks real-cloud execution false. Unexpected programming errors remain visible rather than being disguised as provider success.

Prediction key

Models and responsibilities

IaaS, PaaS and SaaS describe capability/control boundaries. Private, community, public and hybrid are deployment categories. Public cloud does not authorize public data. Service-specific responsibilities vary, but data audience, identities, configuration choices and recovery expectations still need owners. A provider-run host cannot decide the workshop’s intended readers.

Scope and network

Narrow academy/dev contains only academy/dev/reports. Broad academy contains all three fixture resources. Segment dev-tools differs from dev; substring similarity is not parenthood. This says nothing by itself about effective IAM permissions.

The baseline network model fails service_listening. The second fails identity_allows. No packets or live policy checks were performed. Opening broader traffic would not establish a running service or intended application authorization.

Storage

Report documents suggest object-style access; a VM disk suggests block access; an application requiring a shared filesystem suggests file access. These are initial interface matches, not universal service selections. Exact consistency, permission, latency and integration requirements still need checking. An unwanted overwrite can be stored durably, so durability alone is not a tested recovery plan.

Scaling

400 rpm × 50% = 200 rpm of target allowance per replica. Ceiling(850/200) = 5 needed. Maximum 4 yields 800 target capacity and 1600 physical capacity. Target is unmet, physical capacity is met and the plan is capped. At demand 0 the configured minimum still plans 2; at 800 it needs/plans 4; at 801 it needs 5/plans 4; at 1700 it needs 9/plans 4 and misses both target and physical capacity. These are model results, not observed latency or autoscaling events.

Zone loss

Baseline four replicas yield target capacity 800; losing zone-a leaves two and 400, below demand 500. Alternative six yield 1200; losing zone-a leaves three and 600, enough at the target. A shared database or faulty common deployment could affect both zones. The exercise provides no SLA or real failover evidence.

Recovery

Data gap is 600−580 = 20 minutes. Downtime is 650−600 = 50 minutes. RPO 15 is missed; RTO 60 is met. Moving the recovery point to 590 changes only the data gap, now 10, which meets RPO. This does not change downtime.

The local restore verifies fixed earlier bytes against SHA-256, writes them to a fresh restore file and confirms its temporary directory was removed. Current source intentionally differs. It does not validate an application, database consistency, cloud key access, regional recovery or a production timeline.

Cost

Always-on compute is 3×720×5 = 10800 fictional credits; storage is 100×2 = 200; transfer is 50×3 = 150; total 11150, 1150 above budget. Scheduled compute is 3×160×5 = 2400; plus 350 gives 2750, 7250 below. Doubling only transfer adds 150 to each total. Storage and transfer do not disappear when only compute hours change. Rates are invented; alerts can arrive after additional usage/charges have accrued.

Change report

ID order: add queue; remove reports; modify web fields public and size. Risk notes cover possible data/service loss from reports removal and increased web exposure. No change is applied. A change in kind is modeled as replacement only by this invented schema. Real provider replacement behavior can differ.

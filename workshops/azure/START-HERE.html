Place resources inside an accountable lifecycle

Use Azure scopes to reason about ownership, inherited controls and deletion consequences.

Learning goals

  • Distinguish tenant, management group, subscription and resource group responsibilities.
  • Trace inherited scope without treating a hierarchy as a complete access decision.
  • Plan a resource lifecycle around dependencies and accountable owners.

An Azure resource rarely exists in isolation. A reporting application needs an administrative home, a funding boundary, an identity directory and a plan for retirement. Azure Resource Manager organizes resources under resource groups and subscriptions, while management groups organize subscriptions for governance. Microsoft Entra tenants provide the directory context. These concepts answer different questions, so placing all four labels in one diagram is only useful when you explain what each boundary controls and who maintains it.

A subscription is an important management and billing boundary; a resource group collects resources managed together through a lifecycle. A resource belongs to one resource group at a time, but resources in different groups can still depend on each other. Grouping by a shared retirement schedule can be more useful than grouping every resource of the same type together. Naming a group “temporary” does not ensure it can be removed safely or that its contents are inexpensive.

Management groups provide an organizing scope above subscriptions. Governance assignments can apply down a scope hierarchy, but inherited context is not a complete authorization verdict. A directory role is not automatically a resource-management permission, and the same display name can conceal different principals. An administrator needs identifiers, scope and assignment details. The local hierarchy exercise deliberately reports ancestry rather than claiming that a list of ancestors proves a person can create, modify or delete a resource.

Consider a fictional reporting service whose application and data storage have different retention needs. Deleting the application group might be appropriate after a pilot, while deleting the data group could violate the retention plan. Record dependencies across those groups before approving retirement. Moving resources also deserves review because not every resource supports every move scenario, and resource identifiers or dependent configuration can matter. A tidy hierarchy is not evidence that a proposed move will succeed without disruption.

Write a lifecycle record with owner, business purpose, environment, funding contact, retention requirement and an explicit disposal decision. Tags can help maintain this record but are not automatically inherited from a resource group by its resources. Check the actual tagging mechanism rather than assuming a visual parent passes down every attribute. Separate a documented ownership convention from an enforced policy. The distinction matters when a resource appears without the expected metadata or when a subscription changes organizational responsibility.

Run the fixed local hierarchy command to inspect ancestry in invented scopes, then compare that receipt with your diagram. Its result is evidence about supplied relationships, not a live subscription inventory or directory discovery. On paper, remove one imagined application group and list dependencies that would require investigation before real deletion. No deletion is performed here. Broader lifecycle administration is enrichment beyond AZ-900 recognition-level concepts, and neither this exercise nor its completion establishes AZ-104 implementation readiness.

Separate directory identity from resource authorization

Reason about Microsoft Entra identities, Azure RBAC scopes and data-plane permissions independently.

Learning goals

  • Separate authentication, directory roles and Azure RBAC.
  • Describe a least-privilege assignment using principal, role and scope.
  • Identify control-plane and data-plane validation gaps.

A successful sign-in establishes an identity context, not unlimited authority over Azure resources. Microsoft Entra ID manages identities and authentication for users and workloads. Azure role-based access control assigns permissions to principals at a resource-management scope. Administrators must connect those concepts without collapsing them. A user who can manage directory objects is not necessarily entitled to change an application server, and a subscription operator is not necessarily entitled to administer the directory that authenticates its users.

An Azure role assignment connects a security principal, role definition and scope. The principal might be a user, group, service principal or managed identity. Scope determines where the assignment applies, including inherited coverage below that point. Start with the task, then identify the narrowest suitable permissions and scope. Assigning a broad role because it makes an error disappear hides the original diagnosis and can create unrelated authority that persists after the immediate work is finished.

Control-plane permissions manage resources; data-plane permissions operate on service data. Their separation varies by service and authentication method, so a resource-management role name alone does not answer whether someone can read a blob. A managed identity avoids distributing an application secret for supported authentication flows, but it still needs appropriate authorization. Removing a stored password from code is a credential-handling improvement, not proof that the workload has minimal permissions or that every dependent service accepts that identity.

For a fictional analyst, distinguish reading a storage account configuration from downloading report contents. Put each requested operation in a ledger with its intended principal and scope. The local model matches explicit synthetic role assignments against requests. It does not implement every Azure RBAC behavior, deny assignment, conditional assignment, directory control or service-specific access mechanism. Read allowed as a model verdict only. A real access review would inspect effective assignments and test authorized operations in the intended environment.

Access also has a lifecycle. A temporary project role needs an owner, a reason, a review date and a removal decision. Group-based assignment can simplify administration, but group membership itself becomes a controlled input that needs review. Privileged access workflows and authentication requirements address different risks from role scope. Do not claim that multifactor authentication makes an excessive role acceptable, or that narrowing a role compensates for an untrusted sign-in. Each control should answer a specific threat or operational requirement.

Run the access command with no credentials and retain its decisions and matching assignment identifiers. Explain one matching request and one nonmatching request using only the fixed data. Then propose a narrower assignment on paper, without modifying a real directory or resource. Your evidence is a permission rationale plus a bounded matching result. Administrative implementation goes beyond the selected AZ-900 concepts, and the model cannot establish that access has been provisioned, revoked or safely validated in Azure.

Distinguish compliant configuration from deletion protection

Treat Azure Policy, resource locks and role permissions as different decision mechanisms.

Learning goals

  • Contrast policy evaluation with authorization and locks.
  • Explain why compliance findings require remediation decisions.
  • Assess a lock without assuming it protects all data operations.

A team can be authorized to create a resource yet propose a configuration that violates organizational standards. Azure Policy helps evaluate resource state and enforce selected organizational requirements. Azure RBAC answers who can perform actions, while Policy addresses properties and compliance requirements. Resource locks provide another layer for restricting selected management operations. These mechanisms overlap operationally but should not be treated as interchangeable labels for security. Each has its own scope, effect and exceptions that administrators must understand.

Policy definitions describe evaluation logic and an effect; assignments apply policy at a scope. An audit effect records noncompliance rather than blocking the action as a deny effect can. A compliance finding therefore needs interpretation before anyone claims prevention. An existing noncompliant resource may require deliberate remediation, depending on the policy effect and configuration. A dashboard with green or red counts also needs evaluation timing and scope context. It is not a substitute for reading what the assignment actually checks.

Resource locks address accidental changes at the management plane. CanNotDelete permits reading and modifying a resource while restricting deletion; ReadOnly restricts changes more broadly and can affect operations that look like reads but use management requests with other semantics. Locks do not universally protect service data-plane operations. A storage lock should not be described as an immutable backup or a guarantee that no blob can be deleted. Service data protection and recovery controls require their own assessment.

In the fictional service, the governance model reports policy findings separately from lock decisions. Keep those output lists separate in your review. A resource can have a missing required tag and still be protected from a modeled delete operation. Conversely, an apparently compliant resource can remain deletable if the relevant lock is absent. The exercise demonstrates why a single “secure” flag hides useful distinctions. It does not deploy a policy, invoke a remediation task or calculate actual Azure compliance.

An administrator should record the intent behind each control: prevent new configurations, detect existing drift, restrict accidental management deletion or constrain a principal. Select the mechanism that serves that intent and document exceptions. If an emergency change requires removing a lock, that is a consequential change to be authorized and audited, not a routine troubleshooting shortcut. If tags are mandatory for billing, record how newly created and existing resources receive them rather than assuming audit alone supplies missing metadata.

Run the governance command and explain each issue and blocked operation using the fixed teaching rules. Next, work a paper scenario in which a required tag is repaired but a deletion lock remains. State which concern is resolved and which restriction persists. The command does not perform that repair. Preserve both the original receipt and the separate proposal. Policy implementation and lock administration here are enrichment beyond AZ-900 overview concepts; real assignments, exemptions, remediation permissions and service behavior remain untested.

Choose durability without confusing it with permission

Compare storage redundancy, access and recovery as separate requirements.

Learning goals

  • Distinguish local, zonal and geographic redundancy.
  • Separate account access from object authorization.
  • Explain why replication does not replace recovery controls.

A reporting archive has several independent requirements: retain bytes during failures, restrict readers, serve authorized requests and recover from mistakes. Azure Storage redundancy choices primarily address the durability and availability of replicated data across specified failure boundaries. They do not decide who should read the reports. Access mechanisms, network controls and recovery features answer other questions. Start with a requirement ledger so that a strong answer about one dimension does not conceal an unanswered question about another dimension.

Locally redundant storage keeps copies within a single physical location in the primary region. Zone-redundant storage distributes copies across availability zones in a supported primary region. Geo-redundant options add replication to a secondary region, with differences in primary-region zone protection and whether secondary reads are available. These labels are not a universal ranking. Supported account types, regions, services and required operations affect the choice. A requirement for secondary reads should be explicit rather than inferred from the word “geo.”

Geographic replication is asynchronous, so a secondary copy can lag behind the primary. A regional failure can therefore involve data loss relative to the latest accepted writes, depending on service state and recovery procedure. Redundancy also replicates legitimate changes and may replicate unwanted changes. An accidentally overwritten report is not necessarily recovered by selecting a more geographically distributed option. Versioning, soft delete, backup or other service-specific protections should be evaluated against the deletion and corruption scenarios the archive actually faces.

Authentication and authorization need a separate decision. Microsoft recommends Microsoft Entra authorization where supported; shared keys and delegated tokens have different handling and exposure risks. A network path to a storage endpoint does not itself grant data access. Conversely, an authorized identity can still fail because network access or name resolution is incorrect. Record the expected principal, operation, endpoint and access mechanism. Avoid copying credentials into a classroom example or treating an account management role as blanket permission to read every object.

The fixed model compares a short list of fictional option capabilities against required features. It selects RA-GZRS for its secondary-read and zone-resilience requirements, while listing missing capabilities for alternatives. That result is not a recommendation for every archive or a guarantee that RA-GZRS is available for the intended account and region. Real selection would include service support, consistency implications, costs, failover behavior and data residency constraints. Those validations remain outside this local exercise and must not be silently assumed.

Run the storage command and explain each missing requirement in ordinary language. Then consider a paper-only archive whose retrieval deadline tolerates waiting for recovery and whose budget is constrained. Reassess requirements before choosing an alternative; do not simply select the cheapest label. Preserve the executed receipt separately from that discussion. This administrative trade-off analysis enriches AZ-900 storage concepts but does not configure a storage account, validate access, measure replication lag or demonstrate readiness to operate a real Azure archive.

Trace routes, filters and private names independently

Avoid declaring connectivity from a route or private endpoint alone.

Learning goals

  • Separate route selection from NSG permission.
  • Explain why private endpoints need suitable DNS resolution.
  • Preserve route ambiguity and incomplete flow evidence.

An application reaching a database needs more than an address. Its name must resolve to the intended endpoint, traffic must follow a suitable path, filtering must permit the flow and the service must accept the application request. Azure virtual networks provide private network boundaries, but their existence does not prove that every resource can communicate. Build a path explanation from source workload to destination service and identify the evidence needed at each step rather than treating connectivity as one configuration switch.

Routing chooses a next hop based on applicable routes. More specific destination prefixes matter, and Azure has additional route-source selection rules that a simple longest-prefix classroom exercise does not reproduce. If two equally specific teaching routes remain tied, report ambiguity instead of inventing a winner. Real diagnosis would inspect effective routes and route origin for the relevant interface. A route toward a firewall, gateway or virtual appliance also leaves that next hop's health and forwarding behavior to be checked separately.

Network security groups filter traffic through ordered rules with priorities and matching conditions. When NSGs apply at both subnet and network interface, both applicable layers need to allow the new flow. A subnet allow cannot cancel a NIC denial. NSGs are stateful, so observations about existing connections may differ from expectations for a newly initiated connection after rule changes. The local model deliberately uses synthetic match flags and new-flow decisions; it does not generate packets or demonstrate connection tracking behavior.

A private endpoint provides a private network interface for a supported service connection. Applications usually continue using the service hostname, making DNS resolution central to the design. Private DNS zones, links and forwarding paths must suit where clients run, including hybrid clients. Merely creating a private endpoint does not prove the client resolves the intended private address. Public endpoint exposure and service authentication must also be reviewed explicitly. Private addressing is a connectivity choice, not a replacement for data authorization.

For the fictional reporting client, keep a ledger of destination name, resolved address, selected route, subnet filtering, NIC filtering and application result. The fixed exercise covers only some of those columns. Its first route case deliberately has two equally specific candidates, and its new-flow NSG case is denied at the NIC after passing the subnet layer. These are independent findings. Resolving the route ambiguity would not by itself change the NIC result, and changing a filter would not establish correct DNS.

Run the network command and retain both the unresolved route selection and the denied flow. On paper, propose a DNS validation plan for a private endpoint without querying real infrastructure. Identify where the client would obtain its resolver and which hostname should be inspected. This is broader administration enrichment, not a complete AZ-900 requirement. No network changes, private endpoint approvals, packet tests or live effective-route checks occur, so the outcome must remain a bounded explanation rather than a claim of working Azure connectivity.

Size capacity without promising application availability

Use demand arithmetic, scaling limits and operational responsibility to review compute choices.

Learning goals

  • Compare VM and managed application responsibilities.
  • Compute required instances and expose maximum-capacity shortfalls.
  • Separate capacity from application health and resilience.

Choosing compute begins with workload behavior and operational responsibility. A virtual machine gives control over an operating system and its configuration, while managed application platforms reduce some infrastructure management work. Containers package an application with dependencies but do not erase responsibility for application security, image maintenance or service configuration. The right choice depends on runtime needs, deployment model, integration constraints and the team's ability to operate the workload. A familiar service name is not a substitute for those requirements.

Virtual Machine Scale Sets help manage groups of virtual machines, with orchestration and scaling capabilities that require deliberate configuration. Scaling is not simply multiplying an instance count. Images, networking, health evaluation, instance initialization and application state all affect whether additional instances can serve requests. A scale-out decision may be correct while new instances take time to become useful. Document the startup delay and the signal that indicates readiness rather than assuming a provisioned machine immediately contributes full productive capacity.

A first capacity estimate divides forecast demand by measured safe capacity per instance and rounds upward. That estimate depends on what was measured: request mix, response-time target, database behavior and background tasks can change the result. Maximum instance settings constrain the requested capacity. A budget, quota or regional limit can constrain it further, but those are separate mechanisms. Recording the gap between required and configured capacity is more informative than claiming that the presence of autoscale guarantees demand will be met.

Autoscale rules need appropriate signals, thresholds, time windows and cooldown behavior. CPU utilization can be useful for one workload while queue length or request pressure may be more relevant for another. Aggressive rules can oscillate or react to noise; slow rules may leave users waiting through a sustained surge. A bounded arithmetic model does not predict those dynamics. It can expose a capacity ceiling, but it cannot tell you whether a real scaling policy reacts in time or whether the application remains healthy.

The reporting fixture requires eight instances under its simplified demand assumption. Four current instances leave a shortfall of four, while the configured maximum permits only six. The model therefore reports insufficient capacity even after capping the scale target. This is a review finding, not a request to increase a quota or spend money. A team should investigate demand shaping, per-instance performance, architecture constraints and financial authorization before deciding whether a larger fleet is appropriate. Availability also requires attention to failure domains and dependencies.

Run the compute command and independently reproduce its rounding and ceiling comparison. Then propose a paper-only response to the shortfall with at least two options and their risks. Increasing the maximum is one option, not the only answer. State what measurements would distinguish the options. This administrative reasoning extends beyond foundational service recognition. No VM is created, no scale rule is configured and no load test is run; the receipt demonstrates arithmetic on supplied values rather than validated Azure application capacity.

A monitoring chart is evidence produced by a collection system, not a direct view of everything a workload experiences. Plan a restore around data loss and dependencies

Separate backup copies, disaster recovery and proof that a restored application works.

Learning goals

  • Distinguish RPO from RTO and successful restore evidence.
  • Order recovery by dependencies and expose missing prerequisites.
  • Explain why a stored backup is not a completed recovery test.

Recovery planning begins with business tolerances rather than a product selection. Recovery point objective describes the acceptable amount of data loss measured in time; recovery time objective describes how long restoring service may take. A backup schedule can contribute to meeting those objectives, but it does not prove either one. Restore duration, application dependencies, access requirements and validation all matter. Ask what the business must be able to do after recovery, not merely whether a backup file or recovery point exists.

Azure Backup protects supported workloads through service-specific backup and restore capabilities. Azure Site Recovery supports disaster-recovery replication and orchestration for supported machines and scenarios. They are related but not interchangeable. A replicated workload can support continuity after an infrastructure failure, while recovering an earlier version after unwanted changes may require a suitable retained recovery point. Choose protections by failure scenario and supported workload rather than assuming any service with “recovery” in its name covers every outage, corruption or deletion.

Restore ordering exposes dependencies. A database may require network connectivity before it can be reached, and an application may require the database before its own health checks can pass. Identity, name resolution, certificates and external services can add further prerequisites. Draw a dependency graph and identify what must be ready before each component is useful. A valid topological order is planning evidence only; it does not measure startup duration or establish that the restored components communicate correctly with each other.

A recovery point older than the allowed data-loss interval misses the modeled RPO even if a restore command would otherwise succeed. That mismatch deserves a clear finding rather than a reassuring statement that backups exist. Conversely, meeting a freshness requirement says nothing about restore duration, application consistency or completeness of the selected data. Keep freshness, restorability and service validation as separate acceptance conditions. A real exercise would compare restored data with expected business records and document any reconciliation work needed before reopening service.

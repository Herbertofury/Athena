Trace AWS identity decisions without inventing an IAM engine

Separate who is calling, what they request and the layers that constrain access.

Learning goals

  • Distinguish a role session from a long-lived identity credential.
  • Trace allow, implicit deny and explicit deny in a bounded example.
  • Explain why a local decision is not proof of real AWS authorization.

An application that reads order receipts needs an identity, a permitted action and an intended resource. Those are separate design choices. In AWS, IAM roles can provide temporary credentials for an assumed role session, avoiding the need to distribute a permanent application access key. The architectural question is not simply whether the developer can log in. It is which workload will act, how it obtains its session, which operations it needs and when that access should end.

Start a permission ledger with principal, action, resource and context. A reader needs a narrowly described read operation on the intended objects, rather than every operation on every bucket. A different component may need to write new objects without deleting existing ones. Keeping those responsibilities separate makes review and later investigation easier. A convenient wildcard is a decision to expand authority, not merely shorthand for a long list. Record why each permission is necessary.

IAM policy evaluation includes default denial and explicit deny, but a classroom evaluator is not IAM. Identity policies, resource policies, permissions boundaries, organization controls and session policies can interact, with important exceptions and principal-specific behavior. Our model separately checks a fictional allow/deny ledger and a required human approval label. That approval gate is a teaching workflow, not an IAM policy feature. A model-level allow therefore cannot establish actual AWS authorization or substitute for the required owner decision.

Separate authorization from authentication and from audit. Authentication establishes an identity or session. Authorization determines whether that identity may perform a particular request under applicable controls. An audit record helps explain what occurred, but its existence does not grant permission. Similarly, encrypting a receipt does not automatically make its readers appropriate. The review should ask independent questions about access scope, credential handling, data protection and the records needed to investigate misuse.

In the fictional receipt service, the read request matches the reader allow, while the write guard applies to a different action. However, the required owner approval is missing, so the local outcome is approval_required. Predict that result before running the command. Discuss a separate paper-only request with a conflicting explicit deny, and another with no matching allow. Keep those paper cases distinct from the actual fixed receipt. This avoids pretending the default fixture executed cases it never received.

Use invented resource labels and no credentials in this workshop. The executable snippet is ordinary local Python, not an AWS CLI request or a policy deployment. Before applying a real design, an authorized team would inspect the actual policy documents, trust relationships, account boundaries and service behavior, then validate the intended requests safely. Your evidence here is a reasoning trace and a list of missing real-world checks. It is not an IAM approval, security certification or production access test.

Explain VPC reachability as several independent conditions

Use routes and security-group ideas without equating a toy path with working connectivity.

Learning goals

  • Distinguish route selection from traffic permission.
  • Explain stateful security-group response handling conceptually.
  • List the missing checks before claiming real end-to-end reachability.

A VPC design describes where network interfaces live, how traffic is directed and which controls permit it. A route table answers where packets for a destination should go. A security group answers whether selected traffic is permitted at an associated resource interface. Neither question replaces the other. A permitted application port cannot compensate for a missing route, and a route toward a destination does not grant permission to use the application listening there.

AWS route tables use destination matching, including the most specific applicable prefix. A default route is a fallback, not evidence that every destination should follow it. A more specific route can direct one destination range elsewhere. Sketch the source subnet, destination, matching route and intended next hop before discussing security rules. Prefix matching is a paper concept here. The local exercise instead uses invented node labels and graph edges without addresses or prefix evaluation. It does not create a subnet, attach a gateway or inspect a live route table.

Security groups are stateful: response traffic for permitted connections is handled differently from requiring a separate independent inbound rule for every return packet. This principle does not mean that all related application behavior is automatically permitted. A separate new connection still needs its own applicable permission. Network ACLs introduce a different, stateless layer with inbound and outbound rules. Our small model does not reproduce connection tracking or evaluate all of these controls, so retain their differences in the explanation.

Calling a subnet public depends on its routing relationship to an internet gateway, but that label alone does not establish that a particular instance is reachable from the internet. Addressing, attachment, route choice, permissions and the application itself all matter. DNS may resolve an unexpected address; a process may be stopped; a host firewall may refuse traffic. A convincing connectivity claim therefore names the source, destination, protocol, port and time of an observed test, not just a subnet nickname.

For the fictional receipt application, the local graph has a route from client through edge and app to db. The policy-edge list permits client to edge and edge to app, but omits app to db. Predict why the full route exists while no fully permitted path does. This is graph reasoning, not prefix matching or security-group evaluation. Keep the omitted gateway state, return traffic, DNS, network ACLs and host behavior on a separate checklist so the graph does not imply real reachability.

The Python command performs local reasoning only and opens no sockets. It is safe to run without an AWS account or network access. Keep a diagram alongside the receipt so another learner can see why the route and policy checks were considered separately. In a real environment, authorized configuration inspection and bounded connectivity tests would be needed. No result from this workshop certifies VPC isolation, exposure, security-group configuration or a functioning production connection.

Choose storage by interface, access pattern and recovery need

Distinguish object, block and shared-file requirements before comparing lifecycle and recovery tradeoffs.

Learning goals

  • Distinguish foundational object, block and shared-file access patterns.
  • Reject a candidate that lacks a required interface.
  • Separate capability matching from proven recoverability and real pricing.

Storage selection starts with how the application reads and writes, not with a familiar product logo. Uploaded receipt assets can be independent objects addressed through an object API. A virtual machine boot volume needs block-device behavior. A group of compatible clients may need a shared filesystem. These are different interfaces and operating assumptions. An attractive price or durability statement cannot compensate for an interface the application does not support. Write the access pattern before looking at candidate services.

Foundational Amazon S3 object usage, Amazon EBS block storage and Amazon EFS shared file storage illustrate these distinctions. The workshop uses S3-shaped, EBS-shaped and EFS-shaped teaching records rather than full product descriptions. Current service portfolios and specialized offerings are broader than this introduction; do not infer that every AWS product fits a single immutable category. The comparison concerns the declared foundational capabilities only. Real selection still needs attachment, client, Region, performance and access-control details.

A capability ledger makes rejection useful rather than arbitrary. Our fixture requires object_api and independent_objects. The S3-shaped record declares both; the block and shared-file records do not. That is sufficient for a local match, but not for a final service recommendation. A real application may also require access latency, maximum object behavior, retention, encryption, concurrency or migration compatibility. Missing requirements can change a decision, so preserve them explicitly instead of claiming that two matched labels capture the workload.

Lifecycle decisions address retention and movement over time. Keeping every object indefinitely can increase retained storage and preserve data beyond its intended use. Expiring data too quickly can remove a needed recovery window. Different storage classes and access patterns can introduce retrieval and timing considerations. This exercise uses no real prices, transitions or retrieval measurements. Describe what must be checked rather than assuming that the lowest headline storage rate produces the lowest complete cost or meets the application response target.

Storage redundancy and recoverable history address different failures. Replication can preserve availability during some infrastructure failures while also copying an accidental deletion or corruption. A backup or version history may help recover an earlier state, but only when retention, access and the restore procedure are adequate. Verify expected content, not just the existence of a restored filename. This is a paper recovery discussion: the capability matcher does not create object versions, perform restoration or validate any provider durability claim.

Run the storage command to inspect the feasible and rejected candidates. Retain the requirements and missing-capability reasons so another learner can reproduce the decision. No S3 bucket, EBS volume or EFS filesystem is created or accessed. A real recommendation would require authorized service configuration review, workload measurements, current cost analysis and a restore exercise. Your conclusion should say that one teaching record meets two declared interface requirements, then identify the most important unanswered question before deployment.

Fit compute capacity to demand and failure assumptions

Compare EC2, scaling and event-driven compute through workload requirements.

Learning goals

  • Relate throughput demand to a stated per-worker capacity.
  • Separate scaling policy from application health.
  • Describe EC2 and Lambda tradeoffs without assuming universal performance.

Compute selection begins with work, not a favorite service name. A receipt processor has an arrival rate, processing time, memory requirement, execution environment and acceptable delay. A steady service with specialized operating-system needs poses a different problem from a short event-triggered function. Amazon EC2 gives control over instances and their operating environment. AWS Lambda provides a managed function execution model with its own runtime, concurrency and execution constraints. Neither is automatically the cheapest or most reliable answer for every workload.

Capacity arithmetic is useful only when its assumptions are visible. Suppose each healthy worker can process a declared number of requests per interval under a representative workload. Divide demand by that capacity and round upward to estimate a minimum worker count. That calculation ignores warm-up, uneven distribution, contention and dependency limits unless you add them explicitly. Treat it as a planning model, not a benchmark. A capacity number copied from another application is a hypothesis requiring measurement.

EC2 Auto Scaling can change group capacity using configured policies and health information. Scaling does not repair every application failure: a newly launched instance may still have bad configuration, an unavailable dependency or a broken release. Health checks need to reflect useful service behavior, and deployment design needs to account for startup and replacement time. Increasing instance count can even increase load on a constrained database. Trace the entire request path before assuming that more compute removes the bottleneck.

Event-driven compute shifts some operational responsibilities but does not remove workload design. Retry behavior, duplicate events, downstream capacity and concurrent executions affect correctness and cost. A short function can still perform the same business action twice unless the application makes repetition safe. A concurrency limit can protect a dependency while increasing waiting time or rejection elsewhere. Document that tradeoff in user-facing terms, such as delayed receipts, rather than presenting a limit as an unqualified improvement.

The fictional capability exercise asks for event_triggered and no_host_management. Both function-shaped and managed-container-shaped records match, so the model reports ambiguity. These labels do not promise identical real event integration: orchestration and triggering must still be designed. Compare runtime needs, persistent-process behavior, workload measurements and operational responsibility to refine the decision. Any worker-count arithmetic from earlier in this lesson is a separate paper planning exercise, not an output of this capability command.

Run the local compute command and retain both feasible candidates and their caveats. No EC2 instance is launched, no Lambda function is invoked and no scaling policy is installed. The receipt cannot establish latency, provider limits, regional availability or production cost. Real selection would require authorized workload measurements and current service constraints. Your result should recommend what to measure next and explain which workload facts could change the choice, rather than declaring a winner from two matching capability labels.

Make duplicate delivery safe at the business boundary

Separate receiving a message from completing and acknowledging its business effect.

Learning goals

  • Distinguish SQS buffering from SNS fanout and EventBridge routing.
  • Explain the crash window between committing an effect and acknowledging delivery.
  • Trace deduplication, retries and dead-letter handling without claiming exactly once.

A queue separates the arrival of work from the availability of a worker. In an upload-processing service, the producer can record that work is waiting while consumers process at a controlled pace. Amazon SQS provides queue-based consumption; Amazon SNS provides publication and fanout; Amazon EventBridge routes events according to rules. These are different interaction patterns, and an architecture may combine them. Choose based on who must receive an event, how work is buffered and what happens when a consumer is unavailable.

Standard SQS queues can deliver a message more than once. That fact matters at the business boundary, not just in a log counter. If a consumer adds an order amount every time it sees a delivery, a retry can charge or credit twice. A stable business identifier gives the application a way to recognize that the same intended operation has already been applied. The identifier must represent the operation correctly; two legitimate purchases must not be collapsed just because their amounts match.

Consider the failure window after a worker commits its business effect but before its acknowledgment is accepted. A later delivery may carry work that already succeeded. Retrying the effect blindly is wrong, while refusing all retries can lose genuinely unfinished work. An idempotent consumer makes repeated handling converge on the intended result. In production this usually requires durable, coordinated state or an appropriate conditional transition. A process-local set in our model illustrates the idea but disappears with the process.

A retry policy also needs a stopping and investigation path. A permanently malformed or unprocessable message can otherwise consume repeated attempts and delay useful work. Dead-letter handling collects such cases for controlled diagnosis and a deliberate replay decision. It does not automatically repair the payload or establish that replay is safe. Preserve the reason, business identifier and attempt history so an operator can decide what correction is needed without silently dropping evidence of unfinished work.

The fictional ledger includes a repeated order and a failing order. Predict the total from successful unique business operations, not from the number of deliveries. Then inspect which repetition is suppressed, which message is acknowledged and which reaches the local dead-letter outcome after the configured attempt count. Keep delivery count separate from business-effect count. This distinction is a useful operational metric because a system can receive many deliveries while correctly applying only a smaller number of unique effects.

Run the fixed Python command without any queue account, network connection or real financial data. The in-memory receipt demonstrates the fixture’s duplicate suppression and retry transitions only. It does not execute SQS visibility timeouts, durable transactions, FIFO behavior or service-level acknowledgment. A real design needs an authorized test of restart persistence, concurrency races, partial failures and replay procedures. Label those remaining tests explicitly rather than converting a successful local ledger into an end-to-end exactly-once guarantee.

Separate relational failover, read scaling and access patterns

Compare database architectures against explicit requirements rather than a single availability label.

Learning goals

  • Distinguish RDS Multi-AZ DB instance and DB cluster standby behavior.
  • Separate read-replica scaling from failover and recovery requirements.
  • Explain why multiple feasible candidates require further evidence.

Database selection begins with the questions the application must answer and the invariants it must preserve. A receipt service may require relational transactions, joined reports, predictable key-based lookups or a mixture of patterns. Amazon RDS provides managed relational database options, while Amazon DynamoDB provides managed key-value and document storage with its own modeling choices. Managed operation does not make access-pattern design optional. Nor does a familiar service name prove that a particular query, transaction or consistency requirement is satisfied.

Availability and read scaling are related but different goals. An RDS Multi-AZ DB instance deployment has a standby for failover that does not serve read traffic. An RDS Multi-AZ DB cluster has two readable standby instances. The words Multi-AZ alone therefore do not identify the read-serving behavior. State the exact deployment form in your recommendation. This avoids a common mistake in which a learner applies the single-standby rule to every Multi-AZ offering or expects read capacity from the wrong configuration.

Readable DB instance replicas use asynchronous replication and can help serve reads; engine and replica-mode exceptions require verification. Replication lag matters when a user expects to read a change immediately after writing it. A read replica is not automatically equivalent to the failover arrangement of another deployment type, and promotion behavior depends on the actual architecture. Ask separately about writer failure, read throughput, acceptable staleness and recovery from a mistaken update. One feature label should not be allowed to answer all four questions without evidence.

Conventional Aurora architecture separates replicated cluster storage from writer and reader compute. Storage redundancy does not imply that an appropriately sized reader is already running and ready to take over under every failure. DynamoDB also requires deliberate key and access-pattern design; it is not a drop-in relational JOIN engine. This lesson does not rank all database products. Instead, it practices identifying when a requirement calls for detailed engine-specific investigation rather than a generic claim that a managed database solves everything.

The fictional decision model evaluates a bounded set of declared capabilities. Its fixture leaves both a Multi-AZ-cluster-shaped candidate and a read-replica-shaped candidate feasible. That ambiguity is useful: the inputs have not fully expressed every deployment and operational requirement. Do not pick the first row merely because it appears first. Add a written question about failover behavior, lag, recovery, engine support or measured load, and explain how the answer could eliminate a candidate or require combining capabilities.

The executable command compares local records; it creates no RDS instance, Aurora cluster or DynamoDB table. It does not run SQL, measure replica lag or initiate failover. Keep the feasible candidate list and the unresolved requirement together in your evidence. A real recommendation requires current engine and Region support, authorized measurements, an operating plan and actual recovery testing. The model’s ambiguity flag is not a defect to hide; it is a signal that responsible architecture still needs more information.

Test failure scope and recovery objectives independently

Distinguish surviving resources, sufficient capacity, data freshness and restoration time.

Learning goals

  • Calculate RTO and RPO comparisons with explicit units.
  • Separate surviving instances from adequate service capacity.
  • Explain why replication is not a universal backup substitute.

A reliable architecture names the failures it intends to tolerate. Losing one process, one Availability Zone and an entire Region are different scenarios with different dependencies and recovery costs. Spreading workers across zones may reduce one failure concentration, but it does not prove that the remaining workers, database, routing and credentials can serve the workload. Draw the failure boundary explicitly. Otherwise an availability claim can quietly slide from one small incident to a much larger disaster without supporting evidence.

Recovery time objective, or RTO, describes the acceptable restoration interval. Recovery point objective, or RPO, describes the acceptable age of recovered data. They measure different harms: being unavailable and losing recent work. A service can restore quickly from an old backup, meeting its time target while missing its data target. Conversely, a recent recoverable point can preserve data while a slow restore exceeds the tolerated outage. Report both comparisons separately instead of using one green indicator for recovery.

Survival is also different from capacity. If one worker remains after a zone failure but the application needs two equivalent workers to meet demand, the system has surviving infrastructure without sufficient modeled capacity. Actual capacity is more complicated than a count: workers may have different sizes, warm-up periods or dependency bottlenecks. The exercise intentionally uses an equivalent-worker assumption. State it when interpreting the result so a count comparison is not mistaken for a production load test.

Replication is valuable for availability, but it can reproduce an accidental deletion or corruption. A recoverable history, backup or point-in-time mechanism addresses a different failure mode. Those mechanisms still need access, retained encryption keys, compatible software and a restoration procedure. A backup job reporting success does not prove that the application can use restored data. A meaningful drill checks integrity and dependencies as well as elapsed time, and records the point from which business work can resume.

In the local scenario, app-3 survives the selected zone failure, but the fixture reports insufficient remaining capacity. A 45-minute restoration interval is within a 60-minute RTO; a 20-minute backup age exceeds a 15-minute RPO. Predict all three conclusions before execution. The mixed outcome is the lesson: a successful time comparison does not cancel the capacity shortfall or the missed data objective. Write the consequence of each miss in terms of delayed or lost fictional receipts.

Run the resilience model and preserve its units, thresholds and outcome reasons. No real outage, backup, failover or restore is performed. The fixed numbers are scenario assumptions rather than observed AWS recovery times. A real recovery claim would need an authorized drill with timestamps, integrity checks, dependency validation and measured service behavior under the chosen failure. Your handoff should state which target needs a better design and which evidence remains hypothetical, even when one part of the local result passes.

Match an incident question to the right operational evidence

Use CloudWatch, CloudTrail and AWS Config as complementary evidence sources.

Learning goals

  • Choose telemetry, actor/activity or configuration evidence for a stated question.
  • Separate temporal correlation from a supported causal claim.
  • Explain recording coverage and retention as explicit design decisions.

An incident begins with a question, not a dashboard collection. Users report slow receipt processing after a configuration change. You need to establish whether the symptom is real, when it started, what changed and who or what performed the change. Those questions call for different evidence. A metric can show a latency increase without identifying the actor. An activity record can identify a request without proving its effect on application performance. Keep the questions separate before combining the timeline.

Amazon CloudWatch supports operational visibility through metrics, logs, alarms and dashboards. Useful evidence depends on appropriate instrumentation, dimensions, collection and retention. A graph labeled latency needs a defined measurement point and aggregation interval; an average can hide a small population of very slow requests. An alarm threshold is an operational choice, not a guarantee that every user-visible failure will trigger it. The lesson classifies fictional evidence and does not configure agents, dashboards, alarm actions or workload telemetry.

AWS CloudTrail provides records of AWS activity that can help answer actor, action and time questions. Recording scope matters: management-event history and configured trails or other recording choices are not a promise that every application operation and data event is present by default. A missing record can mean missing coverage, retention or an incorrect search, not necessarily that no action occurred. State the source and scope whenever an audit conclusion depends on the absence of an event.

AWS Config tracks recorded resource configuration, relationships and rule evaluations. It can help compare before-and-after resource state, while CloudTrail helps explain an API activity and CloudWatch helps show the symptom. A rule’s compliant result means something specific about that rule and recording scope. It is not blanket regulatory compliance or proof that the application is secure. Combining these sources is often useful precisely because none independently answers every operational and governance question.

Reconcile synthetic costs without pretending a budget is a cap

Keep units, ownership, omissions and alert timing visible in cost decisions.

Learning goals

  • Compute a subtotal from explicit synthetic quantities and rates.
  • Distinguish a budget notification from a guaranteed spending ceiling.
  • Identify missing cost drivers and governance decisions before a real estimate.

A useful estimate states what is being counted, over which period, at which rate and in which currency. A bare total hides assumptions that often dominate the decision. Compute usage, retained storage, requests, transfer, logging and backups may change independently. Some architectures also introduce fixed or minimum charges and licensing questions. This workshop uses invented integer-cent values to make the arithmetic inspectable. None of the rates or totals is a quotation for an AWS service, Region or account.

Match the units before multiplying. A storage amount measured at one instant is not automatically a full month of retained storage. A request count is not a data-transfer volume. An average demand can conceal a burst that changes capacity or concurrency needs. Write one ledger row for each modeled category and mark omitted categories explicitly. An incomplete estimate can still support learning if its exclusions are clear; presenting it as a complete bill would be misleading.

Cost optimization is a requirements problem as well as an arithmetic problem. Removing redundancy can lower a hypothetical subtotal while violating a recovery objective. Retaining fewer logs can reduce storage while undermining investigation. Selecting a lower-priced storage option can add retrieval delay or other charges. Compare feasible designs against the same workload and obligations before choosing the lowest subtotal. The cost lesson should not undo the security, recovery and evidence requirements established earlier in the workshop.

AWS Budgets can track actual or forecast costs and provide notifications or configured actions. Billing and notification delays mean spending can pass a threshold before someone responds. Existing resources can continue to incur charges, and configured actions have their own scope and constraints. A budget is therefore not a guaranteed hard spending cap. Make the response owner, expected action and delay assumptions explicit. An alert with no responsible person or permitted response is only a signal, not an operating control.

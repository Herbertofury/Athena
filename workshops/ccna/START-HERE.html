Separate VLAN membership from successful delivery

Follow VLAN-scoped MAC learning and allowed trunk membership without treating either as end-to-end connectivity.

Learning goals

  • Trace source learning and destination lookup within a VLAN.
  • Compute effective trunk membership from both ends.
  • Distinguish a switching decision from a delivered application request.

A switch forwarding decision begins with the frame and its ingress context, not with the application name printed on a diagram. An access port places ordinary untagged endpoint traffic into its configured access VLAN. A trunk carries traffic for multiple VLANs, subject to its configuration. Before following a destination MAC address, establish which VLAN the frame belongs to and whether each candidate egress port participates in that VLAN. Otherwise a plausible-looking path can cross a boundary that does not exist.

A learning bridge records the source MAC address against the ingress port in the relevant VLAN. It then looks up the destination within that same VLAN. A known unicast destination normally identifies one eligible egress port; an unknown unicast is flooded only through eligible forwarding ports in that VLAN, excluding ingress. Learning a source does not establish the destination's presence. The same written MAC value in another VLAN must not silently satisfy a lookup in this VLAN's forwarding context.

Trunk availability is a relationship between endpoints. If one end permits VLANs 10 and 20 while the other permits 20 and 30, their allowed-list intersection contains only 20. That arithmetic is useful but incomplete: trunk operation, VLAN existence, native-VLAN agreement and spanning-tree forwarding state also matter. An intersection result is not evidence that frames were tagged correctly or received. Keep allowed membership separate from operational state, especially when a configuration excerpt is the only evidence available.

Consider an office where engineering and visitors attach to the same physical switch but occupy different VLANs. A learned engineering MAC does not make the visitors' unknown destination known. Nor does sharing an uplink authorize communication between the VLANs. Inter-VLAN traffic requires a Layer 3 path and any applicable policy. Start your worksheet with VLAN, ingress, source, destination and eligible egress ports. This makes it possible to explain a flood without incorrectly describing it as a broadcast delivered to every physical port.

When a laptop moves between ports, subsequent source frames can update the learned location. Real switches also age dynamic entries and may implement security features that change behavior. The supplied fixed model teaches selected forwarding decisions, not aging, actual frame reception, switch capacity or attack protection. A local list of egress ports is therefore a predicted action under stated assumptions. Real validation would need authorized observations of interface state, VLAN configuration, forwarding tables and the particular traffic under investigation.

Run the fixed VLAN exercise and reconcile its learned entries and forwarding decisions with your worksheet. For a paper counterfactual, remove the required VLAN from one trunk endpoint and identify which membership result changes before considering higher layers. Do not repair the result by adding an imaginary route. Preserve whether the destination was known at each step, because event order matters. Completion demonstrates reasoning about a supplied switching trace; it does not demonstrate that a VLAN or trunk was configured on Cisco equipment.

Worked example

Trace the four fixture events in order. Event 1 learns 02:00:00:00:00:01 on deskA in VLAN 10 and returns flood_unknown_unicast with egress [uplink]. Event 2 learns the other source on uplink in VLAN 10, then returns known_unicast with egress [deskA]. Event 3 learns the first MAC on uplink in VLAN 20, a separate entry, and floods toward deskB. Event 4 is drop_vlan with no egress because deskA does not admit VLAN 20. trunk_intersections.uplink is [10, 20], not every VLAN mentioned by either endpoint. The learned list has three entries, not two global MAC identities. On paper, remove VLAN 20 from one trunk allowed list: recompute that intersection and mark which later learning/forwarding assumptions fail. No real trunk is changed.

Explain a loop-free tree without inventing convergence

Rank a root and least-cost paths while keeping real STP roles, states and timing outside the simplified model.

Learning goals

  • Explain why redundant Layer 2 paths need loop control.
  • Compare bridge identity and cumulative root path cost.
  • List tie-break and convergence evidence missing from a graph model.

Redundant links improve the options available after a failure, but Ethernet forwarding cannot safely use every Layer 2 cycle without a loop-control mechanism. Broadcast and unknown-unicast frames can circulate and multiply when bridges keep flooding through a cycle. A frame has no IP-style hop limit that solves this bridging problem. Spanning Tree Protocol organizes a loop-free forwarding topology while retaining physical alternatives. The resulting logical tree should not be confused with removing redundant cables or proving that recovery will be fast enough.

Root election uses bridge identifiers, with the lowest identifier winning the comparison. In relevant VLAN-aware implementations the identifier includes priority information and an extended system identifier as well as the bridge MAC address. A lower numeric priority is more preferred. The root is not selected because an administrator thinks its model number looks fastest. Record the compared identifiers and the scope of the instance before describing the result, since separate instances can make different forwarding decisions over the same physical topology.

Nonroot bridges compare paths toward the root using accumulated path cost. A lower-cost indirect path can be preferable to an expensive direct link. Equal-cost cases need protocol tie-break rules involving bridge and port information rather than a convenient arbitrary choice. The workshop graph calculation intentionally stops short of reproducing every BPDU comparison. If the fixture does not provide the necessary tie-break inputs, do not claim it has calculated all operational root, designated and alternate ports on a real switch network.

Traditional STP and rapid variants differ in state transitions and convergence mechanisms. Rapid PVST+ applies rapid spanning-tree behavior per VLAN in Cisco environments. An edge-port assumption can allow faster forwarding for an endpoint connection, while BPDU Guard addresses unexpected bridge participation on appropriately configured edge ports. These are not interchangeable settings and should not be enabled indiscriminately on links between switches. Their correct use depends on the intended topology, device behavior and an approved configuration, none of which this local graph establishes.

Build a drawing with the root candidate identifiers beside nodes and costs beside links. Sum each candidate route to the root before choosing the least-cost path. Then draw the remaining physical links differently from the selected logical paths. This distinction keeps a redundancy discussion honest: an unused forwarding path can still be physically available. A graph result cannot tell you how many frames were lost during a failure, whether inconsistent configuration suspended a port, or whether a protection mechanism placed an interface into an error state.

Run the fixed loop-control exercise and retain the root and cost evidence exactly as returned. In the paper counterfactual, increase the cost of one selected link and recompute the affected route rather than asserting an immediate switchover. List the BPDU, port-state and timing observations that a later authorized equipment exercise would need. The current output is a topology reasoning receipt, not an STP capture. It supplies no convergence measurement and no guarantee that the physical network is free of loops.

Worked example

The selected root is named root. Both left and right have root_cost 4 with candidate_neighbors [root]. The edge switch has root_cost 8 and candidate_neighbors [left, right], so its status is equal_cost_not_fully_tiebroken. The right-hand cost remains 8 while the left-hand alternative becomes 11; identify the unique least-cost candidate without inventing port roles or a convergence time. Check bundle compatibility before promising bandwidth

Reason about LACP participation and member consistency without treating a port channel as unlimited per-flow capacity.

Learning goals

  • Distinguish active, passive and static channel modes.
  • Check member compatibility before accepting a bundle.
  • Separate aggregate capacity from per-flow behavior and failure evidence.

A bundle groups compatible physical links into one logical interface, reducing the number of independent links that higher-level features must consider. EtherChannel is Cisco terminology for this family of capabilities; LACP is a standards-based negotiation protocol used to establish suitable aggregation. A bundle is not simply a drawing with several lines between the same switches. Each member must satisfy the relevant local and peer requirements, and the resulting logical interface must be operational before it can carry the intended traffic.

LACP active mode initiates negotiation and passive mode responds. Active with active or active with passive can negotiate, while two passive endpoints do not initiate the exchange needed to establish a channel. Static on mode does not use LACP negotiation and should not be described as another LACP participant. Mode compatibility alone is insufficient. Administrators must also examine the member attributes and platform rules, including appropriate speed, duplex and Layer 2 or Layer 3 configuration consistency for the particular bundle.

For a trunk bundle, allowed VLANs and related trunk settings deserve careful comparison. A mismatch can make a member unsuitable or produce an operational problem depending on the platform and exact configuration. The workshop deliberately uses an explicit compatibility contract instead of promising one universal device response. Read the returned rejection reasons as model findings. Do not turn them into fabricated switch log messages or assume that every Cisco software release reports the same state for every mismatched attribute.

Traffic distribution normally selects members using a hashing policy. A bundle of two links can offer more aggregate capacity across appropriate traffic patterns without doubling the speed available to one particular flow. Which packet fields feed the hash and how a platform handles failures are implementation details that must be checked. Counting cables is therefore not a performance test. Distinguish configured membership, negotiated membership, distribution behavior and measured application performance when explaining why a busy transfer may still be limited by one member link.

Use a compatibility matrix with one row per endpoint pair and columns for negotiation mode and compared member settings. Mark a failed prerequisite before making any capacity estimate. A candidate that fails the mode test does not become a valid channel because its speeds match; a candidate that negotiates is not automatically acceptable if required member settings conflict. Preserve all reported reasons rather than stopping at the first attractive explanation. This gives the eventual operator a clear investigation order without suggesting a live corrective command.

Run the fixed bundles exercise and compare its decisions with your matrix. For a paper counterfactual, replace one passive endpoint with active while leaving other mismatches untouched, then state which finding might change and which cannot. Do not claim a working bundle until every modeled requirement is satisfied, and even then label real negotiation unperformed. Future authorized validation would require actual port-channel state, peer details and failure observations. This exercise sends no LACP frames and measures neither bandwidth nor application continuity.

Worked example

Therefore all_compatible is false. Keep both m3 reasons in your matrix, since fixing speed alone cannot satisfy the supplied VLAN condition. In the paper alternative, change one of m2’s passive endpoints to active. That removes the both-passive obstacle under the model but does not repair m3 or prove that a real channel formed. Separately explain why two compatible physical links still would not guarantee twice the throughput for a single hashed flow. No speed or bandwidth value in this receipt is a measurement.

Separate IPv6 address meaning from neighbor discovery

Classify IPv6 addresses and membership while keeping reachability, ND and default-router evidence distinct.

Learning goals

  • Recognize link-local, unique-local, global and multicast roles.
  • Calculate IPv6 prefix membership without assuming reachability.
  • Explain what neighbor discovery and router advertisements add.

IPv6 expands address space, but good troubleshooting still begins by asking what an address means in context. A host can hold several addresses with different scopes and lifetimes on one interface. A link-local address supports communication on its local link; a global-unicast-shaped address does not itself prove global connectivity. Unique-local addresses serve local communications under a different addressing plan. Multicast addresses identify groups rather than a single interface. Do not infer a usable application path merely from an address that parses successfully.

Compressed hexadecimal notation changes presentation, not address identity. Leading zeroes can be omitted within a group and one consecutive run of zero groups can be represented with a double colon. Comparing strings is therefore a poor way to decide whether two addresses are equivalent or share a prefix. Parse the value and apply the prefix length. The workshop uses deterministic address arithmetic to classify fixed examples and test membership; it does not assign those addresses to interfaces or verify that any endpoint owns them.

Link-local unicast belongs to the fe80::/10 range, while unique-local addresses are within fc00::/7 and multicast uses ff00::/8. The documentation prefix 2001:db8::/32 exists for examples rather than real public deployment. Scope classification is separate from a routing decision. A link-local next hop requires interface context because the same local-link address can appear on different links. A displayed address without that context may therefore be insufficient to identify the intended neighbor even when its syntax is valid.

IPv6 Neighbor Discovery uses ICMPv6 for functions including neighbor address resolution, router discovery and reachability-related mechanisms. Neighbor Solicitation and Advertisement messages are not ARP packets with longer addresses. Router Advertisements can supply default-router and prefix information, while host address configuration can involve SLAAC, DHCPv6 or other arrangements. Receiving an address and learning a default router are related operational concerns but not interchangeable evidence. A worksheet should reserve separate fields for interface addresses, prefixes, router information and neighbor-cache observations.

A common reasoning error is to treat same-prefix membership as proof that two endpoints can communicate. The endpoints still need appropriate interfaces, neighbor discovery, policy and functioning links. Likewise, accepting all ICMPv6 as irrelevant noise can break essential behavior; filtering decisions need to understand message purposes. The local model sends no solicitations and cannot detect duplicate addresses, stale neighbors or missing advertisements. It teaches address interpretation so that later observations can be framed accurately, rather than pretending arithmetic substitutes for those observations.

Run the fixed IPv6 exercise and record each classification and prefix result before drawing a proposed communication path. In a paper counterfactual, keep the address unchanged but move it to a different link and explain why link-local neighbor context matters. Separately list the observations needed to distinguish missing router information from failed neighbor resolution. The result demonstrates bounded address reasoning only. No IPv6 stack is configured, no router advertisement is emitted and no real neighbor or default router has been discovered.

Worked example

The supplied prefix is 2001:db8:42::/64 with prefix_length 64. Address 2001:db8:42::7 has in_prefix true, while 2001:db8:43::7 has in_prefix false. Both use category other_unicast in this model; neither is a claim of public routability, and 2001:db8::/32 is documentation space. fe80::1 is link_local, fd00::1 unique_local, ff02::1 multicast, :: unspecified and ::1 loopback. neighbor_observation is advertisement_seen, but reachability_proven stays false. Treat that string as invented fixture evidence rather than an observed packet. On paper, place fe80::1 on two distinct interfaces and explain why an outgoing interface is needed to identify the intended neighbor. Prefix arithmetic cannot resolve that operational ambiguity.

Separate route installation from forwarding lookup

Keep longest-prefix matching, administrative distance and floating-route assumptions in the correct order.

Learning goals

  • Select the most specific matching destination prefix.
  • Compare administrative distance only in the appropriate route-selection context.
  • Explain when a floating static route can become useful.

A forwarding problem starts with the destination address and the available routes. Several prefixes may match that destination, including a default route and a more specific subnet. Longest-prefix matching chooses the most specific matching installed prefix for forwarding. A route with a shorter prefix does not win just because its administrative distance is lower. Write the matching prefixes in order of specificity before discussing route preference, or the explanation can accidentally exchange two different stages of routing behavior.

Administrative distance expresses local preference among route sources for the same destination prefix. It is not a measurement of latency, physical distance or path bandwidth. Different protocols also have their own metrics for selecting paths within their routing processes. Real routers build a routing information base using those processes and then populate forwarding structures. The fixed exercise simplifies these stages into explicit candidates, so its documented selection order is a teaching contract rather than a complete implementation of every Cisco routing process.

A static route points toward a next hop or outgoing interface according to its configuration and platform rules. A floating static route uses a less preferred administrative distance than the route it is intended to back up. Its usefulness depends on the preferred route no longer being installed and on the backup next hop remaining resolvable. A failed application alone does not necessarily withdraw a preferred route. Health detection, tracking and failure scope need separate attention before describing a static backup as automatic service recovery.

Consider a destination covered by both a /24 and a /16. The /24 is more specific, even if the /16 has a numerically lower administrative distance. Among candidates for the same /24, preference can matter. If the model finds equally preferred candidates and lacks an additional tie rule, it preserves ambiguity rather than choosing whichever appeared first in a file. That is a useful discipline: order in an input list is not evidence that a network device would choose that next hop.

A route-selection receipt is only one part of a packet journey. The next hop must be reachable through an appropriate interface, link-layer resolution must succeed and policy can still block delivery. Return traffic may follow a different path and require its own analysis. The workshop does not emit packets or reconstruct live forwarding tables. Keep a route-choice ledger separate from an end-to-end test plan, and use exact prefixes and addresses rather than an informal statement that traffic goes toward the internet.

Run the fixed routing exercise in two stages: select same-prefix candidates by preference, then perform longest-prefix lookup across those modeled installed routes. For a paper counterfactual, withdraw the preferred candidate rather than merely declaring its application unhealthy; recompute which backup becomes eligible. Preserve any unresolved tie and list the extra information required to resolve it. A later authorized equipment exercise would need actual installed-route, next-hop and failure-detection evidence. This command changes no routing table and does not demonstrate a floating route taking over on a real router.

Worked example

First build the modeled installed candidates separately for each prefix. primary, the /24 candidate with AD 90, is inactive; floating therefore supplies the active /24 at AD 200. default supplies /0 at AD 1 and specific supplies 192.0.2.64/26 at AD 220. Next perform longest-prefix lookup for 192.0.2.77 across those candidates. The /26 wins, so selected is [specific], prefix_length is 26, admin_distance is 220 and decision is unique_route. Lower AD on the broader /24 or /0 does not defeat that more-specific match. On paper, withdraw specific; the floating /24 then wins while primary remains inactive. Reactivating primary would change same-prefix selection, not the longest-prefix rule. No failure detection or route installation is executed.

Learning goals

  • Compare relevant OSPF neighbor prerequisites.
  • Compute cumulative path cost within a supplied graph.
  • Distinguish a compatible peer from a verified Full adjacency.

OSPF is a link-state routing protocol, so understanding its path choices requires more than spotting a neighbor address. Routers establish neighbor relationships, exchange appropriate link-state information and calculate paths using a view of the topology. A graph with neatly labeled costs skips several operational steps. Before using it as an explanation, identify which assumptions establish that the routers can exchange information and whether the graph represents a synchronized link-state database or merely a teaching fixture supplied by the exercise author.

For intended OSPF neighbors, relevant prerequisites include compatible area configuration, timers, authentication where configured and appropriate network relationships. Network type and addressing affect expectations, while mismatched MTU can interfere with adjacency progression. Router identifiers must be suitable and unique in the routing domain. A checklist that finds no modeled mismatch is not proof of Full state. Packets may still be blocked, an interface may be passive or a configuration detail outside the checklist may prevent the expected exchange.

On multiaccess networks, designated and backup designated routers reduce the number of adjacencies needed for database exchange. Neighbor state expectations depend on the network type and router role, so a neighbor that is not Full with every other router is not automatically broken. Point-to-point relationships have different expectations. The workshop does not simulate this election or state machine. Keep the distinction between neighbors and adjacencies visible instead of treating every discovered router as an identical participant in a complete mesh.

Once the supplied topology is accepted as an input, path calculation adds link costs along candidate routes and chooses the least total cost. A two-hop route can cost less than a direct edge. Costs are protocol values, not latency measurements, and their practical interpretation depends on configuration such as reference bandwidth. The local shortest-path result does not prove that a real router installed the corresponding route or that its database matches a peer. Troubleshooting should follow the dependency order. Keep ordered policy separate from address translation

Trace first-match ACL decisions and static NAT facts while distinguishing DNS, DHCP and time-service evidence.

Learning goals

  • Evaluate an ordered access list without skipping an earlier match.
  • Separate static NAT address mapping from permission and delivery.
  • Identify the distinct service evidence needed for names, leases and time.

A network service can fail even when addressing and routes appear plausible. Policy, translation, names, dynamic configuration and time each answer different questions along the path. Combining them into a single statement such as “the network is working” hides important uncertainty. This exercise focuses its executable portion on two bounded decisions: an ordered packet-filter rule list and an independent static address mapping. The surrounding worksheet asks which DNS, DHCP and NTP evidence would still be needed before diagnosing an actual application failure.

An access control list is evaluated in order. The first matching entry determines the action; a later permit cannot rescue traffic already matched by an earlier deny. Standard and extended IPv4 ACLs offer different matching capabilities, and placement and direction matter when applying policy. Real Cisco configuration also includes details such as wildcard-mask interpretation that the local explicit-network model does not reproduce. Write the packet's source, destination, protocol and ports beside each candidate rule and stop at the first applicable match.

A static NAT mapping associates addresses across a translation boundary. It is not an authorization rule and does not by itself prove that a connection can be established. The translated address may still be unreachable, policy may deny the traffic or a return path may be missing. Dynamic NAT and PAT introduce additional pool, port and state considerations outside this fixed exercise. Keep the packet-filter verdict and mapping evidence in different columns so a visible public address is not mistaken for a permit decision.

DNS associates names with records and requires its own evidence, such as the queried name, record type, responding server and actual response. DHCP supplies leased configuration through a separate exchange; a relay forwards relevant messages between client and server networks when configured. A valid lease does not ensure correct DNS data or application service. NTP supports clock synchronization, which helps correlate logs and can matter for authentication. An unsynchronized timestamp can make two correct log entries appear to describe the wrong sequence.

Consider a host explicitly denied before a broader HTTPS permit. The later permit looks reassuring when viewed alone, but ordered evaluation retains the deny. An independent static translation for that host does not contradict the policy result because the mechanisms answer different questions. A good investigation record identifies the exact matched rule, the mapping if present and the untested operational dependencies. It does not invent a DNS lookup, lease renewal or synchronized clock merely because the fixture contains recognizable addresses and service names.

Add a proposed evidence request for DNS, DHCP and time, each tied to a specific uncertainty. This bounded model sends no traffic, changes no ACL or NAT table and confirms neither a live lease nor a synchronized device clock.

Check security compatibility without claiming an RF survey

Combine client capabilities, minimum security policy and a simple channel comparison while preserving RF uncertainty.

Learning goals

  • Separate SSID identity, authentication requirements and client capability.
  • Evaluate a security minimum without downgrading it to make a match.
  • Explain what a channel-overlap model cannot say about real RF performance.

A wireless connection depends on several independent conditions: a suitable radio link, compatible capabilities, an allowed security method and a working network behind the access point. Seeing an SSID addresses only part of that problem. An SSID identifies a wireless service set, not the strength of its security or the correctness of its VLAN mapping. Record the intended service, client capability and organizational minimum before recommending a network, rather than treating the most visible or strongest-looking signal as automatically appropriate.

WPA2 and WPA3 describe security families with different modes and requirements. Personal and enterprise deployments use different authentication arrangements; an enterprise design can involve 802.1X and an authentication server rather than a shared personal passphrase. WPA3-Personal uses SAE, while protected management frame requirements and transition behavior need careful platform-specific attention. A capability label in a fixture simplifies these details. It cannot prove that credentials, certificate validation, authentication-server policy or the client implementation would satisfy a real deployment's requirements.

Compatibility and acceptability are separate judgments. A client might support a network whose security falls below the required minimum, or a securely configured network might require capabilities absent from that client. Lowering the minimum solely to make the client connect changes the security decision rather than fixing compatibility. The worksheet should preserve both failure types. A defensible recommendation could be to use a different approved device or seek a reviewed design change, without inventing permission to weaken an actual wireless policy.

Radio planning also requires more than selecting a channel number. In 2.4 GHz deployments, commonly used 20 MHz channel plans can reduce overlap by separating appropriate channel choices, subject to local regulations. Channel width, channel availability, transmit power, neighboring networks and physical conditions all matter. A simple frequency-spacing model can highlight potential overlap between selected channels, but it cannot measure signal-to-noise ratio, airtime contention, hidden nodes or the effect of walls and moving users on a real client.

Access points and controllers divide responsibilities according to architecture. Controller-based, autonomous and cloud-managed designs differ in management and forwarding arrangements. Roaming decisions and authentication behavior also depend on clients and infrastructure. The local eligibility list does not create a WLAN, attach a client, verify a controller path or test roaming. Keep the architecture drawing separate from the fixture result, and label every proposed RF observation with the location, channel width and measurement conditions that would make it useful in a later authorized survey.

This exercise does not scan local networks, collect identifiers or contact an access point; it demonstrates bounded compatibility and planning reasoning rather than an operational wireless assessment.

Review a typed configuration diff before any API change

Use JSON and desired-state reasoning to distinguish data validation, planned changes and real REST execution.

Learning goals

  • Preserve JSON types and reject misleading comparisons.
  • Explain create, update and remove operations in a desired-state diff.
  • Separate HTTP semantics and dependency planning from an executed transaction.

Network automation begins with a precise description of state, not with a loop that sends commands quickly. Desired state records the intended values; observed state records what an observation reports. A diff compares them under a declared identity and type contract. Without that contract, a renamed interface can look like a deletion and creation, or a string containing digits can be accepted where a number was required. The local exercise reads fixed JSON-shaped data and produces a plan without contacting any device or controller.

JSON distinguishes objects, arrays, strings, numbers, booleans and null. Object member names are strings, but their values need not be. The number 20 and the string “20” should not become equivalent merely because printing them looks similar. Likewise a boolean is not a VLAN number even if a programming language happens to allow arithmetic with it. Validation should reject invalid shapes and types before computing changes. Keep missing fields distinct from intentionally empty or null values when the contract assigns them different meanings.

A desired-state comparison uses stable identifiers to match records. An identifier present only in desired state implies creation under this model; one present only in observed state implies removal; shared identifiers require field comparison. An unchanged field should not appear as an update simply because another field changed. This granularity makes review safer and explains the scope of each proposed action. Removal is a consequential real-world operation, so a printed plan must not be mistaken for permission to delete an actual interface or service.

REST-oriented APIs expose resources and use HTTP methods with defined semantics. GET retrieves a representation, while other methods can create, replace, modify or remove resources according to the API contract. Idempotence describes the intended effect of repeating an identical request, not a guarantee of identical response codes or zero side effects in logging. Authentication, authorization, pagination, asynchronous completion and concurrency controls also matter. The fixed diff exercise sends no HTTP requests, obtains no tokens and does not validate a controller's particular endpoint behavior.

Dependencies constrain execution order even when individual changes look correct. A new upstream object may need to exist before a dependent object can reference it. A successful topological ordering only shows that the supplied dependency graph has a usable order; it does not ensure atomicity, rollback or idempotent recovery after partial failure. Good plans record preconditions, expected observations and failure handling. They also avoid blind retries after uncertain outcomes, because repeating a creation can produce duplicate resources when the service does not provide an appropriate idempotency mechanism.

Run the fixed automation exercise and explain each create, update and remove entry using its stable identifier and exact changed fields. For a paper counterfactual, change a numeric VLAN to a string and state why validation should reject it instead of silently coercing it. Then sketch a dependency-aware review plan with explicit stop points for uncertain outcomes. Label all API actions unexecuted. The resulting receipt is a typed comparison of supplied records, not a device backup, a controller transaction or evidence that configuration drift has been repaired.

  • Retain contradictions and distinguish them from missing observations.
  • Prioritize unperformed validation without claiming full CCNA coverage.

A network review needs a chain of defensible claims, not a folder containing ten successful command exits. A local receipt can establish that a fixed algorithm returned a result for a fixed input. It cannot establish that a campus network is configured, secure or ready for service. The capstone combines selected findings from this workshop so that you can practice deciding what each item supports, which conclusions conflict and what evidence would still be needed before an operational decision could be made.

Begin with one intended service flow: an endpoint in a particular VLAN needs an application through a routed and filtered path. Original practice checks

A route exists but the relevant ACL denies the service. What should the review say?

  1. The route automatically overrides the ACL
  2. NAT guarantees success
  3. The application must be running
  4. Routing evidence does not erase the modeled policy contradiction
Answer and reasoning

D. Routing evidence does not erase the modeled policy contradiction Independent mechanisms answer different questions; a route does not authorize denied traffic.

How should absent neighbor evidence be represented?

  1. As an unresolved claim requiring an appropriate observation
  2. As a successful ping
  3. As proof the router is broken
  4. As an irrelevant detail
Answer and reasoning

A. As an unresolved claim requiring an appropriate observation Missing evidence is uncertainty, not success or a specific failure diagnosis.

What does completing this workshop establish?

  1. Complete CCNA coverage
  2. Practice with selected local models and explicit gaps
  3. Production network approval
  4. Real Cisco configuration proficiency
Answer and reasoning

B. Practice with selected local models and explicit gaps Bounded offline work cannot substitute for the omitted objectives and equipment-based validation.

Limits

No operational acceptance, exam readiness, full CCNA coverage or live network validation is established. The capstone aggregates selected synthetic findings and does not discover an actual network.

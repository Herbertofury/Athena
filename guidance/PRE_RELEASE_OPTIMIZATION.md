# Pre-release optimization gate (zero-loss)
 
Owner directive, 2026-11-24. This is an additive project-owned release standard for Athena and the owner's repositories. It complements the existing [performance acceptance](PERFORMANCE_ACCEPTANCE.md), runtime proof, product invariants, supply-chain and third-party skill security standards; it does not change the versioned 16-document governance bundle or grant new permissions.

## Absolute no-removal and genuine-performance rule (owner directive, 2026-11-25)

This is mandatory for every repository, task, optimization tool, refactor, port, and release; it supersedes any conflicting optimization permission, discretionary budget, or earlier tradeoff in this document or local agent instructions.

- **Absolute preservation:** Never remove, disable, hide, cap, truncate, sample, downgrade, or sacrifice existing features, content, records, assets, providers, supported formats/platforms, integrations, accessibility, UI controls, quality, correctness, compatibility, data, tests, or coverage to optimize performance, size, or resource use. No exception, even as a last resort. No deleting files, modules, assets, or source merely to shrink or accelerate a product. Replacing a proven inefficient internal implementation with a fully equivalent or improved implementation is allowed; eliminating redundant computation, allocations, or duplicate work is encouraged, not removing capabilities or content. Do not use shrink-anything's destructive cut/cleanup routes as an optimization tactic; use its read-only diagnosis and verified non-destructive improvements. Preserve all existing test coverage.
- **Fundamental engineering first:** Profile true cold and warm startup, hot paths, complete workloads, end-to-end latency, tail latency/hitches, throughput, and CPU/GPU/RAM/disk/network/power as applicable. Challenge the causal architecture, algorithms, data structures, allocations, locking, serialization, filesystem/network I/O, rendering and native boundaries. Use reviewed [Fast Anything](https://github.com/EL4CTEO/fast-anything), [Rust Anything](https://github.com/erkamyaman/rust-anything), and the strongest compatible Rust/C++/native libraries, SIMD, parallelism and other proven technologies. Compare candidates, including boundary overhead; do not force a language rewrite. Persist verified improvements as the new baseline.
- **No cheap tricks:** Never manufacture speed through benchmark prewarming, test preparation that differs from ordinary use, artificial limits, viewport virtualization/culling, content-visibility suppression, reduced fidelity, skipped work, fake readiness, concealed loading, or shifting mandatory work/cost to a later interaction or background job. Actual cold-start and full-completion performance must be measured separately. Do not introduce prewarming, speculative prefetching, lazy/deferred loading, or similar perceived-speed techniques as the primary solution; exhaust reasonable causal alternatives and try harder to solve the underlying bottleneck first. Only as a documented last resort may a genuinely non-lossy supplementary technique be proposed, with explicit owner approval, evidence of alternatives tried, and full end-to-end proof of no cost shifting or regressions. Ordinary correctness-preserving caches, incremental invalidation, batching and deduplication are legitimate when they actually reduce equivalent work and do not mask cold performance; preserve cold-path proof. Absolute preservation and the prohibited benchmark/content tricks above are never waivable through this fallback.
- **Promotion gate:** Compare exact baseline and candidate on identical hardware/settings/data with real cold and warm runs, repeated representative and worst-case workloads, complete output/feature equivalence, p50/p95/p99 and relevant resource metrics. Reject any material regression beyond measured noise, hidden tradeoff, or incomplete work. A requested optimization campaign must produce a real measured gain; if a candidate fails, profile and pursue a different engineering approach rather than using shortcuts. Do not call an unverified or preservation-only optimization a win. Record evidence and rollback; test the actual shipped/runtime artifact. Ordinary releases with no verified safe gain may retain the baseline after mandatory applicable assessments; do not force destructive changes.

## Required at every release candidate

The owner distinguishes mandatory optimization from opt-in dedicated security audits. Before every release, run shrink-anything, fast-anything and rust-anything on all applicable changed source/workloads, or reuse recorded results from those same tools for exactly unchanged relevant inputs. Each applicable named tool must actually complete its assessment; another tool, a timeout, unavailable executable, lack of time or a deferred pass is not a substitute. Missing applicable core evidence blocks checkout until resolved. For genuinely unsupported scopes (e.g. documentation-only or a native Rust component with no eligible port), record specific inapplicability and evidence; never force a port. Keep every independently verified zero-loss improvement as the new baseline; a completed pass with no safe win is a legitimate outcome. Run assessments early during development and bound experiments, not the mandatory assessments. Existing project-specific checks, platform controls and authorization boundaries remain intact.

### Trusted sources and isolated execution

- [shrink-anything](https://github.com/EL4CTEO/shrink-anything): [upstream README](https://github.com/EL4CTEO/shrink-anything/blob/main/README.md).
- [fast-anything](https://github.com/EL4CTEO/fast-anything): [upstream README](https://github.com/EL4CTEO/fast-anything/blob/main/README.md).
- [rust-anything](https://github.com/erkamyaman/rust-anything): [upstream README](https://github.com/erkamyaman/rust-anything/blob/main/README.md).

Before installation/execution, inspect the exact upstream version, license, source, dependency/install scripts, MCP/agent capabilities and applicable security advisories; record an immutable commit or package version and artifact digest where available. Use verified official distributions and a disposable, least-privilege worktree/container with local tools/caches and synthetic fixtures. Do not run remote scripts blindly, use global setup, transmit private code/data to external agents/services, expose secrets, touch production databases or run with production credentials. Respect the project's license and the user's authorizations. Do not override existing pinned toolchain constraints. Never modify third-party code or distribute assets without rights.

## Opt-in security maintenance (off by default)

Security scanning is a separate, explicitly requested maintenance lane, never an automatic dependency of the standard release checkout, including high-risk and hotfix lanes. No required receipt result, mandatory CI status, automatic installation, automatic scan or automatic remediation is added by this standard for safe-anything, Semgrep, cargo-deny, cargo-audit, dependency vulnerability scans, secret scans, agent configuration audits, or other dedicated security assessments. Enable per task/repository only on explicit owner request; scope and tools must be identified. When opted in, report findings, errors and coverage separately as advisory evidence, not a scanner exit-code release gate. A scan that is not requested, skipped, unavailable, incomplete, or reports findings is not a passed scan and does not by itself block release. Do not suppress findings or claim a clean bill of health.

This separation does not authorize deliberately introducing known exploitable defects, leaking secrets, breaking authorization, dropping existing project-required checks, ignoring actual data loss/correctness regressions, or weakening GitHub protections. Triage actual known material defects and preserve existing rights, provenance, artifact integrity, and safe tool execution; these are not an obligation to run dedicated vulnerability audits. Fuzzing and Miri for behavioral equivalence, memory correctness and crash regressions remain risk-routed functional verification, not a compulsory security audit. Security-only campaigns are opt-in.

### safe-anything (opt-in)

- Official source: [erkamyaman/safe-anything](https://github.com/erkamyaman/safe-anything), [README](https://github.com/erkamyaman/safe-anything/blob/main/README.md), [rules](https://github.com/erkamyaman/safe-anything/blob/main/docs/rules.md). Upstream describes pattern-based checks for source, secrets, agent/MCP setup, mobile/cloud/CI configuration and locked dependencies; not proof of absence of vulnerabilities.
- After reviewing and pinning the exact distribution, use a scoped read-only scan of an authorized disposable checkout, for example `safe-anything . --offline --json`. Offline mode skips OSV dependency checking; online dependency scanning transmits package names/versions to OSV and needs separate authorization for that external access. Do not scan private home directories, credentials, or unrelated repositories.
- Keep redacted reports local; triage false positives and skipped/unsupported paths. Upstream excludes some generated files, binaries and large files; zero findings do not certify safety. Do not blindly apply suggested fixes, install MCP globally or upload SARIF. If the owner requests CI integration, use a separate manually invoked advisory job, with reviewed pinned code and no required release status. No such workflow is installed by this policy.

## Mandatory stack freshness

Before every release, complete the [web acquisition and frontier-stack advancement standard](WEB_ACQUISITION_FRONTIER.md). Refresh official version and channel evidence for the actual shipping stack, adopt verified compatible upgrades with no material regression, and complete the mandatory fix-forward repair procedure before any older-version hold. A hold requires a failed bounded repair with retest evidence or a documented infeasibility constraint, plus a next review. Evaluate stronger relevant crawler/browser/download technology without requiring speculative rewrites. The release receipt must include the `stack_freshness` gate, with a bounded reuse/drift review for touched capabilities under the [shared capability coordination policy](../docs/REUSABLE-PACKAGE-COORDINATION.md). Dedicated security audits remain opt-in.

## Mandatory wiki closeout and product review

At each material checkpoint and before release, complete the [wiki closeout standard](WIKI_CLOSEOUT.md). Document the actual app and all user-facing workflows; verify changed instructions on the real supported deliverable, inspect unnecessary steps and duplicated work, fix safe verified improvements, and publish/read back the actual live Wiki when required. Add `documentation_closeout` to the existing single receipt. Existing documentation generators and verified evidence should be reused; heavy retrieval or diagram tools are risk-routed, not blanket dependencies.

## Execution route

Follow the [CLI-first non-interruptive execution standard](CLI_FIRST_EXECUTION.md) throughout checkout: prefer native commands and structured APIs, use tested CLI-Anything harnesses for missing supported interfaces, and reserve foreground desktop interaction for explicitly authorized unavoidable cases. Preserve real runtime evidence using isolated test sessions where possible. No additional universal harness-installation gate is introduced.

## Sequence

1. Establish a clean, recoverable baseline of the exact release candidate: commit SHA, supported platforms, toolchain, original test inventory, builds, native/browser/game workflows, representative workloads, expected outputs/side effects, package size and applicable performance/resource metrics. If the baseline fails, diagnose first. Check dynamic loading, reflection, plugin registries, serialization, compatibility paths, external asset links, and generated data.
2. **Shrink**: run `shrink-anything doctor`, `scan` and applicable `weigh` on the build. Do not run destructive `cut` or deletion-oriented agent tasks; use read-only attribution and non-destructive, equivalent-work improvements with a strong passing baseline and explicit file scope. Keep all tests, public API, registered IDs, documentation, source evidence, translations, release assets, user data and original content; no deletion as an optimization strategy and no test weakening. Run `verify` and `report`; undo rejected cuts. No tests or insufficient dynamic coverage: scan only, record blocker/limitations.
3. **Fast**: use `fast-anything doctor` and `scan -- <representative command>` on supported runtimes. Profile before changing anything; use the measured slow path, not a toy benchmark. For a worthwhile candidate, use `port`, agent implementation, `verify`, and isolated `enable` plus `bench`/ `report`. Reject if end-to-end work, correctness or resource cost regresses; disable rejected ports and restore the original. Existing native Rust paths use native profiling, not needless bridging.
4. **Rust**: use `rust-anything profile`/ `analyze` for applicable workloads and evaluate the best eligible hotspot or migration candidate. For a selected unit, use the upstream documented bridge/record/build/diff/fuzz/bench/gate/report loop; keep original fallback/disable route. Record and replay equivalent side effects as well as values/errors. Run generated-input recording in isolation: upstream warns it executes real original code repeatedly. Fast and Rust may propose the same change: compare on independent branches from the same baseline, not stacked bridges. Promote only the best verified implementation. Whole-app rewrites are not a release obligation and require a separately justified scope and parity plan.
5. Run independent checks after each candidate and the combined final candidate: full baseline tests (including test inventory and coverage parity), new adversarial cases, supported-platform builds, lint, build and applicable functional dependency/packaging and license obligations (dedicated security audits are opt-in), API/ABI and save/data migrations, exact end-to-end workflows, cold/warm startup, responsiveness, throughput, peak memory and CPU/GPU/I/O/network/power where relevant. Use repeated interleaved runs on equivalent data/hardware; record p50/p95/p99 or frame/tick tails as applicable and measurement noise. Benchmark the shipped build including bridge, runtime, install, disk and startup overhead. Protect accessibility, quality, completeness, portable-folder data, offline mode, compatibility and fallback. No faster-by-doing-less. An improvement must be material beyond noise in at least one target dimension, with no material regression in any protected dimension or undisclosed tradeoff. No hard-coded speedup promise.
6. Keep all individually verified zero-loss wins, with incremental commits and reproducible rollback. Restore failed/neutral/unmeasured experiments; never delete user files, caches outside the worktree, existing evidence or other agents' work. Re-run acceptance on the exact promoted head. Report blocked items honestly; do not call a missing check a pass. If all applicable passes are completed and no safe win exists, the unchanged baseline is acceptable for ordinary releases (not proof of improvement for an explicitly requested optimization task).

## Release checkout v3: confidence without release paralysis

The owner requires an exceptionally effective, fast release checkout across all repositories. Optimize for verified risk reduction and genuine user-visible gains per minute, not tool count, percentage of code deleted, or number of green badges. Do essential checks continuously on changed code, leaving the release candidate with only the final evidence reconciliation and artifact smoke checks. Do not force the entire tool catalog onto every project.

### Risk lanes and default extra-work budgets

These are suggested **additional discretionary experiment/review budgets**, not timeouts that waive the three mandatory core assessments or correctness. Classify the actual diff, dependency graph, generated output, release platform and changed user workflows; raise the lane whenever risk is unclear. Existing project-required checks always take precedence.

| Lane | Typical scope | Checkout strategy | Extra discretionary budget |
| --- | --- | --- | --- |
| Quick | Documentation, metadata, data-only corrections, small low-risk fixes | Relevant existing checks, schema/link/provenance checks as applicable, structural diff review, core tool applicability decisions, final artifact smoke | Up to 5 minutes |
| Standard | Ordinary features, bug fixes, dependency/packaging changes, routine releases | Quick lane plus affected integration tests, changed-path lint and functional dependency checks, one representative equivalent-work benchmark and the three applicable core tool passes | Up to 15 minutes |
| High-risk | Unsafe/FFI, authentication behavior, storage/migration, concurrency, game/runtime/renderer, installer/updater, large compatibility change | Standard plus risk-specific tests: real supported environments, replay/rollback, fuzz/Miri or targeted profiling as appropriate; wider matrix where needed | Up to 30–45 minutes of exploratory work; mandatory evidence may take longer |

An urgent security or regression hotfix uses the smallest **sufficient** scope with the affected mandatory gates and release smoke, not a loophole for unsafe publication. Reuse recent valid evidence for unaffected components; record the follow-up deeper audit when appropriate.

### Required fast path and intelligent routing

- Establish exact candidate identity, target platforms, changed components, risk lane, affected workflows and relevant last-good baseline. Run the project's existing build, tests, lint/type checks and required native/integration checks. Reuse existing tools and commands rather than installing redundant ones.
- Run independent read-only checks in parallel when safe; deduplicate overlapping analyzers; serialize destructive or resource-contentious work. Benchmarks run isolated from other CPU/GPU/disk-heavy jobs. Do not oversubscribe machines or block the UI unnecessarily.
- Reuse verified tool installations, dependency/build caches and test evidence keyed by exact relevant source inputs, lockfile, build flags, tool/runtime version, OS/architecture and fixture/workload identity. Changes to shared dependencies, configuration, tests, security rules or target environment invalidate affected evidence. Never reuse stale evidence for a changed path or claim a prior run proves a new release artifact.
- For shrink/fast/rust, run all applicable named tools every release or reuse their valid results for exactly unchanged relevant inputs. Record completed assessment evidence or genuine inapplicability for each. A deferred or failed applicable assessment is a hard checkout blocker. Only experiment on a material, causally supported opportunity within the available budget. Compare overlapping port proposals independently; no double bridges. Prefer native algorithms, data structures, caching and batching over gratuitous migrations. Do not force a rewrite or keep an unmeasured change.
- Run additional non-security tools according to the matrix below, or equivalent reviewed project tools. Dedicated security audits stay off unless explicitly opted in, irrespective of risk lane. Use focused checks by default, full checks when risk/coverage demands it, and report unsupported platforms or missing evidence explicitly.
- Limit ordinary optimization to one bounded challenger pass and at most one focused follow-up for a clear promising candidate. Stop on diminishing returns, no material win, incompatibility, or budget exhaustion. Preserve rejected/deferred exploratory candidates (not deferred mandatory core assessments) as a concise actionable Athena/project backlog entry, not a lingering experimental patch. No retry loops to manufacture a passing result; diagnose flaky tests and retain the failure evidence.
- Re-run checks invalidated by accepted changes; do not restart the entire checkout unnecessarily. Verify exact final candidate, actual packaged artifact (digest, reproducible build where supported, license notices, clean install/launch/update/rollback as relevant), and release notes. Separate fixture, native and deployed evidence.
- In ordinary releases, ship once all mandatory gates pass, all retained changes are independently verified and all three applicable named core assessments have completed. A sound unchanged baseline with no safe win is a valid result. Deep comparative work, large rewrites, long fuzz campaigns and broad audits belong on separate branches or scheduled/manual maintenance runs unless required to resolve a release blocker. Do not create unsolicited background jobs or make a deep optimization campaign the default dependency of a release.

### Promotion and hard-stop rules

**Hard blockers:** missing, deferred or failed applicable core optimization assessment; known material regression, failing mandatory functional checks, data loss/corruption, broken promised platform/workflow, artifact integrity or distribution rights failures, missing required native/real-runtime acceptance, or unverified optimization retained. An opt-in scanner's absence, status or raw findings are not release gates. Actual known material defects must be triaged, not hidden. Resolve or revert the candidate. A time budget is never a waiver. Existing project gates remain intact; earlier optimization tradeoffs cannot override the absolute no-removal and genuine-performance rule above.

**Nonblocking opportunities:** optional optimization tool unavailable, no promising candidate, neutral candidate, exploratory timeout, any unrequested or incomplete dedicated security audit. Record reason and next action; never represent these as passing tests. A tool finding is triaged based on evidence, not merely its exit code; a real blocker must be fixed even if found by an optional tool.

### Compact evidence and continuous improvement

Keep a single release receipt, not duplicate reports from every tool. Link to existing CI logs and artifacts; record exact candidate and baseline, lane and selection reasons, mandatory check outcomes, per-core-tool outcomes, selected extra tools, accepted/rejected experiments, measurements, known limitations, artifact digest and rollback. Capture elapsed time and cache reuse so Athena can improve checkout efficiency itself. Evidence must match final candidate and real target; never invent receipt fields. Store the receipt outside the candidate commit (CI artifact or release attachment) to avoid self-referential SHA changes.

Maintain reusable, sanitized benchmark fixtures and evidence in the owning repository and link successful methods or failed hypotheses to Athena's research/backlog. Promote verified gains as the new floor. Future releases should learn from historical regressions, test failures, slow checks and unnecessary duplicate work. Record deferred improvements without blocking a sound release, and prioritize them in later maintenance.

### Lightweight receipt validation (optional CI integration)

Use [release_checkout.py](tools/release_checkout.py) after existing project checks and artifact verification, not as a substitute for them. It is Python standard-library only, performs no network calls, tool installation, subprocess execution or source mutation, and checks a JSON receipt of at most 1 MiB. It can be invoked in a project-specific release workflow using a reviewed pinned copy of the script, with the exact candidate SHA resolved independently by the checkout/CI (not read back from the receipt).

```sh
python guidance/tools/release_checkout.py --receipt /path/to/release-receipt.json --head "$(git rev-parse HEAD)"
```

Receipt schema version 5 (versions 1–4 are superseded; regenerate rather than silently reinterpreting old receipts):
- Required: `schemaVersion: 5`, full `head` and `baseline` commit IDs, `lane` (quick/standard/high-risk), nonempty `scope`, `hard_blockers: []`, and boolean `retained_optimization`.
- `checks`: map of mandatory check names to objects with `status: "passed"` and nonempty `evidence` pointing to actual results. Minimum check categories: `project_checks`, `workflow_acceptance` (including protected features/data/portability), `artifact_integrity`, `artifact_rollback`, `review`, `stack_freshness` (official-source stack inventory, decisions, dates and evidence), `documentation_closeout` (verified user guide and simplification review). High-risk adds `risk_specific`; retained optimization adds `optimization_equivalence`. Include additional mandatory project gates; a failing declared gate is rejected. For docs-only scope, appropriate schema/provenance/content/packaging evidence is sufficient, not a fictitious executable test.
- `core_tools`: all three named core tools mapped to objects containing `status` (adopted/no_safe_win/not_applicable), `evidence` with result or specific reason, and for completed applicable passes nonempty `tool_version` and `command` documenting the actual named-tool run (or exact-input evidence reuse). Deferred/failed/missing applicable passes cannot validate. An adopted core change requires `retained_optimization: true`. Optional extra tools, measurements, exact commands, tool versions, artifact digest, elapsed time, rejected candidates and limitations can be linked or stored alongside the receipt per the release evidence requirements.
- `checks.stack_freshness.holds`: explicit list (empty only if no older-version holds). Each hold requires nonempty `component`, `retained_version`, `candidate_version`, `reason`, `repair_evidence`, and `next_review`; `repair_status` must be `attempted_unresolved` (actual causal repair and retest did not pass) or `infeasible` (specific documented constraint prevents a repair). Record official source/version evidence in the linked inventory. Use an explicit unknown candidate version only when upstream information is unavailable. A successful repair must be adopted, not listed as a hold. The validator checks the receipt structure, not whether the repair or inventory evidence is truthful or complete.
- `checks.documentation_closeout`: in addition to `status: "passed"` and `evidence`, require `documented_head` equal to the independently supplied candidate SHA, nonempty `coverage_evidence`, `walkthrough_evidence`, `simplification_evidence`, and `publication` object. Publication mode `live_wiki` requires nonempty `url`, `readback_evidence`, and full `wiki_commit` SHA; mode `repository_docs` requires nonempty `url`, `readback_evidence`, and `reason` explaining why the deliverable legitimately has no required Wiki. An existing/required live Wiki cannot use the repository-only exception. The validator checks structure, not the actual wiki, coverage, workflow or truth of the claims. Keep publication evidence external to the candidate SHA to avoid self-reference.
- Optional `security_audits` is a separate advisory map; omit it when not opted in. No security-audit outcome is required for validation. Do not put dedicated audit results into the mandatory `checks` map; existing externally required project statuses remain governed by their own controls.
- Exit 0 means structural consistency only; exit 1 means a missing/failed gate or inconsistent receipt; exit 2 means unreadable/malformed/oversized input. The validator cannot verify that a linked artifact or claim is genuine, determine risk scope, prove that a tool executed, enforce GitHub branch protection, or establish runtime acceptance. Agents must verify the actual evidence independently.

Regression tests are in [test_release_checkout.py](tests/test_release_checkout.py); run `python -m unittest discover -s guidance/tests -p test_release_checkout.py -v`. Add this inexpensive check to existing release jobs only after project-local validation. Do not duplicate the whole test pipeline or make installation of all 25 tools a universal CI dependency.

## Release evidence

In the release notes or a repository-local evidence receipt, record: baseline/final SHA; date; tool versions/commits and provenance; per-tool applicability, exact commands and exit status; test inventory/coverage and platform/workflow results; workload/hash or fixture identity; before/after measurements with units, repeats and uncertainty; accepted/rejected candidates and reasons; rollback/fallback instructions; remaining blockers. Keep raw/private logs local and publish only sanitized evidence. Distinguish fixture, real runtime and deployed release verification. Do not publish credentials or source traces. Require an independent test/review of retained optimization results, not a self-declared pass. For a no-change optimization pass, reconcile existing evidence rather than adding a redundant review ceremony.

## Additional stack-specific verification

- Rust: cargo fmt --check, cargo clippy, cargo test and cargo bloat or equivalent when available; Criterion or a reproducible harness; feature/target matrix and portable packaging. Check unsafe/FFI behavior, ABI and distribution rights; cargo audit/deny only by opt-in.
- JS/TS: project build/test/lint, real browser/native integration, bundle analysis and functional dependency checks; dedicated dependency security audits only by opt-in. Preserve dynamic imports and runtime registrations; no removal as an optimization strategy.
- Python: project tests, import/entrypoint and package checks, profiling and platform packaging. Keep dynamic discovery and script compatibility.
- Java/Minecraft and Sims mods: actual supported loader/game builds and representative in-game client/server or CAS/mod-library workflows; preserve registries, assets, saves, script imports, frames/ticks and feature parity. A synthetic benchmark or build is not native game proof.
- Knowledge/data repos: verify source provenance, counts, IDs, relationships, full query results and export/restore; no deleting records or citations merely for size. A release with no executable hot paths can mark port tools not applicable.

This document is a mandatory agent instruction, not proof of installed executables, a completed optimization run, CI enforcement, or a versioned governance-bundle release. Mechanical release gating should be added through each project's existing CI with reviewed pinned tools, real workload adapters and evidence validation; do not blindly run agent-assisted source mutation from release CI.

# Continuous web acquisition and frontier stack advancement

Owner directive, 2026-11-24. Applies to Athena and every consuming repository, alongside the existing CLI-first, modernization, and mandatory optimization standards. Athena owns shared research into better crawling, browsing, extraction, monitoring, and downloading. The release objective is the strongest current compatible stack, with measured evidence and no loss of functionality.

## Mandatory pre-release freshness

- Inventory the shipping stack: runtime/compiler, direct and resolved transitive dependencies, browser/renderer, driver, storage, network and download components, build/package tools, provider API versions and fixed platform/game compatibility targets. Use the actual manifests and lockfiles; documentation-only repositories review their relevant publishing tools.
- Before each release, refresh official registry/release metadata, changelogs, and compatibility documentation for the applicable stack. Prefer observations made within 24 hours of checkout; reuse relevant exact-input evidence. Distinguish stable, prerelease, nightly, local binaries, SDKs, distro packages and hosted services. Do not assume the latest GitHub release is the latest version on all channels.
- Prefer the newest verified production-worthy compatible release and current best-fit technology. Stage compatible upgrades early, test and adopt them when no material regression is found. Maintenance, compatibility, and reproducibility improvements count even without a speed increase. Evaluate frontier/nightly candidates when they offer a concrete benefit; do not substitute an unproven preview for a working release.
- Compare equivalent workloads and preserve complete functionality, compatibility, UI fidelity, data formats, portable operation, startup, latency, memory, throughput and relevant resource use. Split regressive upgrade groups, perform the mandatory fix-forward repair pass below, retain all verified compatible improvements, and keep a rollback path. Preserve explicit Minecraft/Sims/runtime/ABI target envelopes. Do not force incompatible version upgrades.
- Record current and proposed versions, official sources and observation dates, adopted or held decisions, evidence, and the next review for holds. A hold requires the fix-forward evidence below, not just an initial failed upgrade, a known upstream issue, or unfamiliarity. Never claim a version was tested or is current if it was not verified.
- Pin resolved versions and lockfiles; run the mandatory applicable optimization assessments on the final stack. Perform the freshness review within existing release budgets; avoid speculative rewrites and expensive unrelated experiments on the critical path. Reuse validated results. Dedicated security audits remain opt-in. Existing permissions and project acceptance criteria remain intact.

## Mandatory fix-forward before retaining an older version

The owner requires an actual repair attempt when the newest eligible version exposes a defect, regression or integration failure. A failed initial test is the start of diagnosis, not a downgrade decision. This applies during development as well as the release freshness review and covers first-party code, dependencies, runtimes, frameworks, engines, build tools, crawlers, browsers and download stacks.

1. Reproduce the defect on the exact newer candidate and compare against the last-good version on equivalent inputs, supported targets and unchanged acceptance criteria. Capture minimal reproduction, logs, output differences, measurements and the causal hypothesis.
2. Investigate root cause: distinguish application misuse, incompatible settings or feature flags, stale transitive dependencies, migration errors, API/ABI changes, upstream bugs and genuine performance regressions. Check official changelogs, migration guides, issue discussions, supported fixes and relevant upstream patches.
3. Implement at least one credible, authorized, causally targeted repair when feasible. Prefer correct migration, configuration or dependency resolution, then local integration changes, compatible adapters, or a narrowly scoped reviewed upstream fix/cherry-pick. Where source and distribution rights permit, a pinned local patch or maintained fork is a candidate; do not modify third-party projects or publish upstream changes without authorization. Never disable required features, weaken tests, hide failures, circumvent access controls, or merely shift cost elsewhere.
4. Retest the repaired newer version on the original failure, adversarial/regression cases and the complete representative workload; verify all protected dimensions and final supported artifacts. Retain and pin the newest repaired implementation when it preserves the last-good floor and its update benefits. Fix unrelated regressions rather than discarding independent verified upgrades. Record reproducible patch provenance, maintenance cost and a plan to remove the patch when an upstream fix is available.
5. Only retain an older version when the bounded repair effort genuinely cannot establish a verified no-loss result, or a specific documented constraint makes repair infeasible (fixed user target, unavailable required source/toolchain, incompatible rights, unsupported platform, or an unsafe/unavailable repair path). Do not invent a repair attempt in such cases. Record the precise defect or constraint, causal investigation, actual repair and retest evidence or evidence explaining why a repair cannot be attempted, retained version, and next action/review. Merely being short of time, seeing one failed test, or preferring familiar code is not enough to justify skipping an otherwise feasible repair.
6. Keep repair work bounded: start early, isolate it from unrelated development, use existing risk-lane budgets and stop after a meaningful targeted repair and focused retest if further work would become disproportionate. If still unresolved, ship the verified last-good compatible version once existing mandatory release gates pass, preserve the failed candidate and actionable follow-up, and reattempt on a later relevant release or upstream fix. Do not restart an unchanged failed experiment without new evidence. A repair not yet attempted remains open, not a verified fallback decision.

Every release receipt must explicitly list all older-version holds (an empty list means no holds), including the repair disposition and supporting evidence. Missing, deferred-without-attempt, or successful-but-discarded repair dispositions do not justify retaining an older version. This is not a mandate to force a new game/runtime target or accept an unsafe or unproven update. It does not change opt-in security auditing or CLI-first requirements.

## Continuous acquisition research

Start with Ghost Downloader 3 and Firecrawl. Maintain a shared candidate catalog with exact upstream links, version channels, documented interfaces, platform support, license/redistribution terms, portable configuration and state, known limits, and measured versus advertised capabilities.

Prefer authorized official APIs, feeds and provider file IDs; use conditional requests and incremental updates where documented. Use direct HTTP before headless rendering when equivalent, and respect documented site and provider access restrictions, rate limits, user permissions and creator rights. Keep local data and browser profiles isolated; use permitted cloud services only with explicit authorization.

Research modular alternatives rather than forcing a single engine into every repository. Candidate categories include direct HTTP, HTML extraction, crawl orchestration, headless browsing, change monitoring, resumable downloads, storage transfers and dependency update discovery.

For download integration, verify expected size and hashes where available, stream to a staging path, support cancellation and resumable partials tied to the correct file identity, and atomically promote validated files. Preserve last-good complete records after failure. Keep project-local state where supported.

## Evidence and adoption

Compare identical inputs and complete outputs on local controlled fixtures or authorized representative workloads. Measure first useful result, full completion, throughput, request count, transferred bytes, startup, peak memory, CPU and latency tails. Exercise pagination, duplicate records, retries, cancellation, interrupted downloads, restart, changed files and invalid results. Record reproducible benchmark instructions and limitations. No unverified superiority claims.

Review new upstream signals during relevant Athena and consumer work. Expand the catalog as better candidates are discovered. Share verified results and reusable adapters with the owning repositories. Prioritize Enderloom, Modhunter, GameSync, Noxviola, Athena and Modding-Knowledge while applying the freshness gate across the ecosystem.

See the [initial source-backed research](../research/web-acquisition-frontier-2026-11-24/README.md) and [candidate registry](registry/web-acquisition-watch.json). This is guidance and a research queue, not proof of installed tools, running autonomous research, executed benchmarks, or completed dependency upgrades.

## Daily discovery mechanism

The [daily/manual GitHub Actions job](../.github/workflows/athena-web-acquisition-watch.yml) calls the [metadata collector](tools/web_acquisition_watch.py). It reads public official GitHub latest-release metadata for the seed registry and up to five new search leads per topic (crawler, browser automation, download manager). It records unavailable observations separately and emits a reviewable JSON artifact, retained for 14 days. It does not install, download or execute candidate software, alter repositories, merge dependency updates, or run target-site crawls. Run it locally with an appropriately authenticated GitHub CLI and `python guidance/tools/web_acquisition_watch.py --output report.json` if desired. The output file must not already exist.

Review these signals during relevant development and before release; verify the actual language/package/SDK channel, license, and compatible target before testing a change. Update the catalog and research receipts after review; the daily job does not automatically claim the leads are superior. It runs outside the release critical path, and its schedule depends on GitHub Actions availability. This is an automated discovery path, not a continuously running benchmark or an autonomous upgrade agent.

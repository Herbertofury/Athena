# Bounded SQLite read-query reference

Added 2026-11-11. **Synthetic correctness/security-policy tests, not a sandbox or production database endpoint.** This reference shows how several independent controls compose around a small, trusted local schema. It is a second foundation alongside the [recovery drill](../sqlite-recovery-drill/README.md).

## Question and scope

Can a local research/catalog app preserve a complete result contract while refusing disallowed database operations and interrupting excessive query work?

The reference opens a fresh read-only connection for each operation. The schema in every test is generated by the test: a three-column catalog, an excluded table with synthetic text and two views. No real database, sensitive content, network request, shell command, dynamically loaded extension, custom SQL function or active Athena runtime route is used.

The normal product-facing interface should expose **application-owned query templates plus bound values**, not raw arbitrary SQL. This module accepts SQL only so the tests can exercise forbidden statements directly. It has no CLI/server endpoint. Its authority policy is specific to this generated schema and is not a general SQL permission system.

## Layered contract

1. Validate finite, positive policy limits and bounded SQL/parameter inputs before opening the database. Reject unsupported parameter types rather than invoking arbitrary adapters.
2. Open an existing database using `mode=ro`. Use a fresh connection, no prepared-statement cache and no persistent callback state shared with other operations.
3. Require and read back defensive configuration, disabled trusted-schema behavior and disabled extension loading. Require query-only mode. Refuse a runtime that lacks these requirements instead of silently downgrading.
4. Set and read back SQLite limits for value/row length, SQL text, column count, expression depth, compound terms, variables and attached databases. These are **limits on specified constructs**, not total process memory limits.
5. Keep a deny-by-default authorizer installed throughout preparation and execution. Allow only SELECT/recursive-query action codes, the explicit catalog fields, and three named built-in functions. Refuse writes, schema changes, PRAGMAs, ATTACH, views, excluded tables and unlisted functions.
6. Install a progress callback with an approximate VM-instruction interval. It can interrupt for callback-count budget, cancellation or deadline. Check cancellation/deadline again between output rows and before returning.
7. Serialize typed row values into a bounded wire representation. Return `state=complete` only after exhausting the cursor and passing all limits. Row/byte overflow raises instead of returning a truncated result labeled complete. BLOBs have an explicit hex wrapper; nonfinite floats are rejected, not silently converted.
8. Close the entire connection on every outcome. The tests verify that the source file's SHA-256 is unchanged after each case.

Default example numbers are **test parameters**, not recommended production defaults. Output bytes count the exact JSON array of rows, including brackets and commas, but exclude the small response metadata. Python object overhead, SQLite allocations, OS cache, input ownership and filesystem work are not bounded by that number.

## Primary-source findings that matter

SQLite's authorizer runs while statements are prepared; execution-time re-preparation can also invoke it. Keep the intended callback installed for the statement's lifetime. `SQLITE_IGNORE` can substitute NULL for a denied read, so this example uses `SQLITE_DENY` to avoid disguising missing data. A table-only count can use an empty column name, and nullable callback arguments must be handled. [AF26016](https://www.sqlite.org/c3ref/set_authorizer.html)

The same source warns that generated-column expressions are authorized when schema is parsed, rather than each DML access. **This is one reason the example's trusted-schema boundary is essential.** Do not extend its claims to an attacker-controlled SQLite file or treat a column-name allowlist as a complete malicious-schema defense. [AF26016](https://www.sqlite.org/c3ref/set_authorizer.html)

Progress callbacks are periodic, with an approximate instruction count, and a nonzero return interrupts work. Since SQLite 3.41.0, complex preparation can directly call the handler too. This is cooperative cancellation, not a wall-clock or CPU-time guarantee; callbacks must not mutate their own database connection. [AF26017](https://www.sqlite.org/c3ref/progress_handler.html)

Runtime limits apply per connection. A requested value can be capped by compile-time limits and the setter returns the previous value, so the reference explicitly reads the resulting limits. [AF26018](https://www.sqlite.org/c3ref/limit.html) SQLite's length limit also applies to the encoded content of a row, while column, expression and parameter limits address different work. They do not add up to a hard RSS allowance. [AF26019](https://www.sqlite.org/limits.html)

Defensive and trusted-schema configuration protect specific SQLite behaviors. They do not isolate the process from malicious native code, compromised libraries or a hostile filesystem. Configuration support must be verified against the actual linked library, not the Python release number alone. [AF26020](https://www.sqlite.org/c3ref/c_dbconfig_defensive.html) [AF26011](https://sqlite.org/security.html)

## Run and inspect evidence

From the engineering directory:

```sh
python3 -m unittest discover -s tests -p test_sqlite_query_boundary.py -v
```

The [final local log](tests-final.log) passes 32 methods on Linux/Python 3.12.14/SQLite 3.53.1. Cases include full results and exact byte accounting, bound-value injection strings, joins/counts, private-table and view/CTE indirection, schema reads/writes, ATTACH/VACUUM targets, extension/function refusal, multi-statement input, row and byte edges, oversized input, invalid policies, expensive joins, deadline/cancellation, nonfinite output, missing-file refusal and connection isolation. Tests verify the interruption reason for the expensive-query/deadline/cancellation paths, not merely any exception.

The [first run](tests-first.log) intentionally remains visible: 27 methods, five errors. The policy initially rejected valid count/rowid access because SQLite 3.53.1 emitted `database=None` with the empty-column read. The correction permits only that catalog empty-column case; attachments, temporary schema and view access remain refused. Positive controls now pass, with additional view/alias/empty-output regressions. Rejecting all SQL would be fail-closed but not a usable solution.

## Disqualifying constraints and next gates

Do **not** adopt this reference as-is if inputs include malicious database schemas/files, arbitrary extensions/UDFs, required views, other tables, cross-account isolation, persistent shared connections or strict CPU/RSS deadlines. Those need a different audited contract. In particular:

- Filename resolution and read-only opens do not establish a hostile-path boundary or prevent all read-time filesystem effects.
- A progress callback cannot guarantee timely interruption of every OS/filesystem wait or native operation.
- A Python exception after some rows were computed is not an externally published partial result here; production streaming needs an explicit incomplete terminal protocol.
- Logging full queries, parameters or denied object names could leak private data. The reference returns generic failures and does not claim a complete redaction system.
- Closing a connection does not roll back external side effects from arbitrary host functions. This fresh-connection reference registers none and only allows the listed built-ins.
- No performance comparison, fuzzing campaign, malicious-file evaluation, cross-platform execution or OS sandbox escape test has been performed.

For actual adoption, freeze the application's required query catalog and schema, test correct positive queries and adversarial negatives, profile complete response delivery, establish the platform isolation boundary, and keep runtime patch/version review separate from benchmark claims.

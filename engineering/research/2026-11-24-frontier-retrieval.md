## Athena architecture candidates and experiments

1. Stable provider-qualified entities and evidence IDs form the source of truth; link every derived chunk, embedding, image, table and recommendation to a source version. Never use a generated answer as a replacement for the source.
2. Use exact ID/path lookup and lexical search first where sufficient. Compare hybrid lexical/vector/graph retrieval, reranking, and query decomposition on a frozen question set with source-level ground truth. Do not rank by raw embedding throughput alone.
3. Incremental content-addressed ingestion: track source/version/hash and dirty records; reuse verified parser/embedding results only for identical content and configuration. Handle deletion, corrections, deduplication, index migration and interrupted writes without dropping history.
4. Test high-volume catalog imports and multi-source joins with identical result counts, IDs, ordering, precision, warnings and durable transactions. Compare existing SQLite/FTS, Arrow, DuckDB, Polars, DataFusion and vector candidates as distinct roles. Separate portable local storage from optional shared services.
5. Batch embeddings, bounded async work, vector quantization and reranking are challenger methods. Measure recall at fixed quality, p50/p95/p99 response, ingestion/update time, total memory, GPU utilization, persistence and index growth; include cold start and failure recovery.
6. A local or approved premium accelerator/service is eligible if evidence supports it; do not favor cheaper infrastructure by default, but include total-system overhead and authorization. No private data or external model calls are implied.

Prioritize Athena's knowledge retrieval, source dedupe, project capability lookup and wiki evidence search. Only promote a specific configuration after matched complete-output benchmarks and actual consumer acceptance.
